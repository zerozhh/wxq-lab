# 第九十八章 · 工具构建：怎么用 wxq-lab 的数据 API 做自定义分析

> **读完这章你能**：不看任何文档，独立跑通「采集→落盘→条件查询→交叉验证」的完整分析链路，并知道哪四个接口可以直接调、哪个参数是坏的、哪些红线碰了就出假数据。

---

## 一、从用工具到造工具

第 84 章讲的是怎么用 wxq-lab 的每个现成功能——看榜单、查 fit、跑复盘。本章是它的反面：当现成功能回答不了你的问题时，怎么自己造一个。这条升级路线在本项目里被反复证明值得走：**整个项目最有价值的几个结论，全部出自自建分析，而不是任何现成页面**。橱窗重复计数伪影是去重脚本发现的；「孙小宾骨架 72.5%」是联合条件查询查出来的；补丁内容是重提取前端数据包 diff 出来的。datawxq 官网不提供其中任何一项。

先给出现有数据能力的全图，避免重复造轮子：

| 资产 | 内容 | 规模 | 现状 |
|---|---|---|---|
| `data/meta/<日期>/` | 每日聚合快照（榜单/趋势/阵容/fit） | 09-14/15/20/21 四日 | 09-20 起源站冻结 |
| `data/heroes.json` 等卡牌库 | 85 英雄（面板+技能+觉醒）、21 棋手、73 装备（合成树）、255 天赋、6 阵营 | 全量 | 可随时重提取 |
| `data/matches/` | 个人对局复盘记录 | 目前为空 | 等你录入 |
| 远端聚合 API | 榜单/趋势/阵容/fit 四类端点 | 聚合基线 1,137,509 局 | 仅 lineups 与 fit 有活动 |
| 远端 explore 端点 | 任意 AND 条件的聚合统计 | 全量池 | 可用，未冻结前是条件查询主力 |

读这张表的关键一行是最后的状态列：数据冻结不是世界末日——**114 万局聚合、54 万局 fit、240 局登顶采样（去重后 120 局唯一）已经全部落盘在 `data/` 里，冻结只是停止增长，不停止分析**。本章的工具链对落盘数据和远端数据一视同仁。

动手之前先回答「什么时候值得造工具」。三个判据，全部满足才动手：一，问题能用数据回答（「下个版本谁强」能，「下局我该不该 D」不能）；二，现有视图确实覆盖不了（MetaView、HeroDetailView、EquipmentFitView、ExplorerView、TierView 已经覆盖榜单/详情/fit/勘探/梯度五类问题，先确认你要查的不在其中）；三，答案会被复用（一次性问题的手工查询成本更低，`explore-sample.mjs` 拉一次数据肉眼看就行）。反过来，最不值得造的工具是「把官网页面重新画一遍」——datawxq 已经画得很好，wxq-lab 的前端价值在于展示**站方没有的加工结果**，比如装备 fit 排序（EquipmentFitView）和 AI 教练（CoachView）。

还有一条前置判断：这个问题值不值得写成脚本而不是手工查。手工查询的上限是一次性、单条件；脚本的门槛是可复现、可组合、可批量。经验法则是——**当你第二次想做同一个分析时，第三次之前把它写成脚本**。comp-query.mjs 就是这么来的：第一轮手工查了 11 套阵容，第二轮补丁后又想查，于是有了带容错和落盘的脚本。

## 二、端点完整文档：四个已确认接口

### 2.1 聚合榜单

```
GET https://api.datatft.com/wzwxq/rankings/heroes?time=7&version=v1
GET https://api.datatft.com/wzwxq/rankings/commanders?time=7&version=v1
GET https://api.datatft.com/wzwxq/rankings/equipment?time=7&version=v1
```

返回英雄/棋手/装备榜单（登顶率、前三率、出场率、中位名次）。`time` 是统计窗口天数，公开无需鉴权。坑在语义：混排池数据、无段位维度，第 79 章讲过的「混排池局限」直接适用——榜单回答「谁在大池子里稳」，不回答「谁在王者局强」。

### 2.2 趋势序列

```
GET https://api.datatft.com/wzwxq/ranking-trends?type={hero|commander|item}&time=7&version=v1
```

返回 6 小时粒度的时间序列，是第 97 章快照 diff 和 `meta-evolution.py` 的原料。已知坑：序列点的起止受源站数据管道状态影响——冻结期 trend-hero 的 28 个 6h 时间点全部落在 09-16 之前，**趋势接口会安静地返回旧数据而不是报错**，用前必须先看最末时间戳。

### 2.3 阵容搜索

```
POST https://api.datatft.com/wzwxq/lineups/search
```

返回热门阵容排行，含英雄/装备名称到 ID 的映射。已知坑最重要的一条：**`heroId` 等过滤参数未生效**——传了也返回全量，你以为在查「含露娜的阵容」，实际拿到的是所有阵容。想做条件过滤必须在客户端自己做。冻结期它和 fit 是仅有的两个活端点，但「活」不等于「可用作条件统计」。

### 2.4 装备适配

```
POST https://api.datatft.com/wzwxq/equipment-fit
```

返回 72 装备 × 85 英雄的 winRateLift 矩阵，约 60 万场样本。冻结期唯一持续增长的数据源（43 万→54 万局），第 97 章痛苦面具 lift 回升 +9.6pp 的补丁痕迹就是从它的四日序列里读出来的。用法警告：**fit-lift 不可单独作为出装依据**（审查发现 #8：贤者之书 +30pp 是选择语境伪影，联合条件查询裁出它倒数第二），证据等级永远是联合条件查询 > fit-lift > 极限局单局。

### 2.5 explore：联合条件查询的主力

四个官方端点之外，`comp-query.mjs` 实际使用的第五个端点是 `POST https://api.datatft.com/wzwxq/explore`——多英雄 AND 过滤的聚合统计，棋手×骨架矩阵、强度梯度表、2977 局三核统计全部出自它。它的官方文档状态是「explorer 查询接口待逆向」：参数语义靠 `explorer-recon.mjs` 勘察反推，`heroId` 过滤同样存在不生效的报道。用它的纪律：每次查询结果先与已知基线对表（比如全局登顶率必须落在 16.7% 附近），对不上就说明参数语义理解错了。

「待逆向」的具体工作方式值得展开，因为它决定了你能不能安全地用这个端点。勘察的标准流程是**控制变量发请求**：固定其他参数，每次只改一个，对比响应差异，反推这个参数到底过滤了什么。三个必须做的对照：空条件基线（验证你拿到的默认池是什么）、已知答案条件（查一个统计已知的组合，比如仅露娜 30600 局 24.3%——数字对上，说明条件语义理解正确）、边界条件（传不存在的 ID，看报错行为还是静默忽略）。第三项最重要：**静默忽略坏参数的接口比报错的接口危险得多**——lineups 的 heroId 就是这种，它不报错，它只是无视你。所有勘察结论都必须写进脚本注释，下次接口行为变化时这些注释是唯一的排查起点。

### 2.6 无 CORS：代理架构是硬前提

这批接口全部**没有 CORS 头**，浏览器直连一律被拦。所以 wxq-lab 的架构是固定的：前端永远不直接碰 api.datatft.com，一切走 `scripts/serve.mjs` 的 `/api/datatft/*` 反向代理（`npm run ui` 后 http://localhost:5177），开发模式由 Vite proxy 转发到 5178 的数据服务器。你写任何新的浏览器端分析页，都必须遵守这个约定；写 Node 脚本则没有这个限制，直接 fetch 即可——这也是为什么本章所有分析工具都是脚本而非页面。

代理层还有两个容易被忽略的细节。其一是 `/api/img` 图片代理：英雄立绘来自 static.datatft.com 与 game.gtimg.cn 两个域名，代理用白名单限定了这两个 host——你新增任何图片源都要改白名单，否则前端全是裂图。其二是接口响应结构与 `ui/src/types.ts` 的 TypeScript 类型一一对应：**接口字段变化最先在类型层暴露**，`npm run build` 的 vue-tsc 类型检查就是免费的接口回归测试。所以「源站改了响应结构」的发现路径是固定的——先 build 报错，再 diff 响应，再修解析层；不要等页面上出现 NaN 才知道接口变了。

## 三、本地数据加工模式：脚本读 JSON

远端查询只负责拿数，重活全部在本地做。模式很简单：Node 22 脚本读 `data/*.json`，输出写回 `data/meta/<日期>/`。三个现成先例值得照抄结构：

- **`comp-query.mjs`**：按阵容条件查询。内置整体容错（超时/解析失败返回 null，绝不崩进程）和增量落盘，查询间 sleep 1.5 秒，遇 42000 封禁码立即中止。这套「容错+落盘+退避」三件套是所有新脚本的模板——长查询跑一半被封是常态，增量落盘保证已拿到的数据不丢。
- **`cmd-comp-query.mjs` / `eq-combo-query.mjs`**：棋手×阵容、装备×装备的联合条件变体。要扩展成「全 21 棋手 × 全骨架矩阵」，改表驱动部分即可，不必重写。
- **`hs-analysis.py` / `meta-evolution.py`**：Python 侧的去重统计与时间序列分析。Python 做统计比 JS 舒服，两边通过 JSON 文件交接，不共享进程。

卡牌库这条线独立于 API：`node scripts/extract-database.mjs && node scripts/split-database.mjs` 在版本更新后重跑，从 datawxq 前端内嵌模块重新提取 85 英雄/21 棋手/73 装备/255 天赋。原理值得懂：datawxq 是 Vue SPA，静态 curl 什么都拿不到；卡牌库整体打包在 `/assets/seo-*.js` 模块里，extract 脚本在站点同源的浏览器环境里 import 该模块后导出——这就是第 97 章补丁还原（seo-Dafcx4m7 → seo-DhBJxZml 全量 diff）的技术底座。

把「写一个新的分析脚本」固化成七步，照做就不会踩前面提过的任何坑：

1. **先写输出 schema**：你要的最终表格长什么样（列名、单位、样本量列必须在场）。schema 想不清楚的分析，跑完也读不懂。
2. **选输入**：远端查询还是落盘 JSON。冻结期默认落盘；需要新条件统计才碰 explore。
3. **抄三件套**：从 `comp-query.mjs` 抄容错（失败返回 null 不崩进程）、增量落盘（每查完一条就写文件）、退避（查询间 sleep 1.5s，42000 即停）。
4. **跑基线校验**：任何条件统计跑完后，先查一个已知答案（全局基线 16.7%/50.0%/3.50 或仅露娜 24.3%）对表，对不上就停。
5. **样本量分档输出**：结果表必须带局数列，<100 局的行打上「方向性」标记——让读者一眼看到哪里是沙子哪里是地基。
6. **写口径披露**：去重规则、窗口定义、条件语义三行注释，附在输出 JSON 的 meta 字段里。
7. **一条命令可复现**：`node scripts/你的脚本.mjs [日期]` 从零跑通，不依赖任何手工中间步骤。

这七步的成本大约是写裸脚本的两倍，但它把「一次性的数字」变成「可复用的仪器」——第五节的项目清单里每一个，本质上都是这七步跑一遍。

## 四、采集基础设施：三层抓取与封禁对策

| 层 | 工具 | 用途 | 速度 |
|---|---|---|---|
| 直连 API | `./scripts/update.sh` | 每日统计落盘 `data/meta/<日期>/`（summary.md + api/*.json） | 秒级 |
| 浏览器全量 | `WXQ_FULL=1 ./scripts/update.sh`（走 `capture.mjs`） | 页面渲染+截获全部 JSON，接口勘察用 | 慢 |
| 定时托管 | GitHub Actions（每日 08:53 `daily-snapshot`） | 本机不可用时的采集冗余 | — |

第三层不是锦上添花，是**封禁对策的基础**：本机 IP 已被 api.datatft.com 封禁（连带 datawxq 官网在自己网络里都渲染 42000 错误），GitHub 机房 IP 也曾被封、一天后解封。目前采集完全依赖 Actions——「采集环境与使用环境分离」是已经用血换来的教训，任何新采集逻辑都应该默认跑在 Actions 而不是本机。

两个补充工具补全这张图。`screenshot.mjs` 是视觉留痕：用 playwright-core 驱动系统 Chrome 截页面快照，接口勘察时用来确认「页面显示的版本号/数据日期」与你抓到的 JSON 是否一致——第 97 章确认「版本：v260917」标注用的就是这类手段。`update-service.mjs` 是常驻化尝试：把每日采集变成后台服务，配合 `serve.mjs` 的 `/api/update-log` 与 `/api/update-status` 端点，让前端能显示数据新鲜度。这两个端点的存在提醒我们一件事：**数据管道的健康状态本身应该是一等公民**——一个不显示数据日期的分析工具，会诱导用户把冻结期数据当成实时数据用，这是比数据缺失更危险的静默失败。

WXQ_FULL 浏览器模式的原理也值得一句话讲透：`capture.mjs` 让真实 Chrome 渲染 datawxq 页面，然后截获页面发出的**全部** XHR/JSON 响应——不是你猜哪个接口要哪个，而是页面自己告诉你它要了什么。这就是「接口勘察」的全部秘密：SPA 的页面逻辑就是最准确的接口文档，让页面替你发请求，你在旁边抄。第一次勘察 datawxq 时用的就是这个方法，四个已确认端点全部由此现形。

礼貌抓取的规则写在项目铁律里：每日 1 次、正常 UA、遵守 robots.txt（datawxq.com 仅禁 /admin）、查询间退避、见 42000 立即停手。这些不是法律问题（接口公开），是**数据源存活问题**——抓得越狠，封得越快，所有人的数据都没了。

## 五、分析项目建议清单：从易到难

按投入产出排好的五个自建分析项目，每个给思路与验收标准：

| 项目 | 思路 | 验收标准 |
|---|---|---|
| 1. fit-lift 复算与交叉验证 | 用落盘的 fit 四日序列复算全部 72 装备 lift，与 #13 的九件完备排名对表，标记所有「两口径矛盾」的装备 | 产出一份「装备证据等级表」，矛盾项全部标注 |
| 2. 全棋手×骨架矩阵自动化 | 把 `cmd-comp-query.mjs` 从 6 候选扩到 21 棋手 × 11 骨架，落盘成一张矩阵 | 每个 ≥200 局的格子给出登顶/前三/均次与置信区间 |
| 3. 补丁快照 diff 报告 | 扩展 `meta-evolution.py`：输入两个日期目录，自动输出位移表+去卷积真值+异动清单（第 97 章的流水线半自动化） | 下个补丁日 30 分钟内出报告 |
| 4. 个人 matches 与 meta 对照 | 先按 `data/schema.md` 录入对局（`data/matches/` 目前为空），再写对照脚本：你的装备/天赋选择 vs 当日 meta 主流 | 每局复盘自动输出 3 条差异点 |
| 5. 抽卡概率实测 | 联动第 93 章的概率模型：用大量截图记录 D 牌结果，检验「各等级各费用概率」的理论表 | 每档 ≥500 次采样，偏差 >2pp 判理论表有误 |

排序理由：项目 1、3 是纯本地计算，零风险；项目 2 消耗远端查询配额，冻结期做不了（落盘数据够）；项目 4 是唯一能把分析对象从「全服玩家」切换到「你自己」的——第 86 章讲过混排池数据对你的参照力有限，真正的因果仪器只有你自己的对局记录；项目 5 是全书唯一需要游戏内实验的，成本最高，放在最后。

其中项目 2 值得多写两句，因为它是现有结论里杠杆最高的一块。棋手×骨架矩阵目前只查了 6 位候选棋手（孙小宾/镜/白歌/常小娥/明先生/瑶妹），而全池有 21 位棋手——剩下 15 位里完全可能藏着下一个 40%+ 的组合，特别是那些「全局数据平庸但特定骨架很强」的类型（瑶妹的反例已经证明棋手榜名次与骨架适配度是两回事）。矩阵铺满后的第二个用途是**反向选骨架**：固定你最想玩的棋手，查他的骨架分布——为镜定制的骨架表和为孙小宾定制的骨架表不该是同一张。三核骨架全量条件 46.6% 里，孙小宾+镜两家占走 58% 的样本（1738/2977 局），「其他所有玩家」只有 14.6%——这个分布本身就是线索：骨架的公开统计被少数专精群体主导，矩阵铺得越满，「谁的强度」这个问题就拆得越细。

项目 4 的另一半价值在复盘侧：`data/matches/` 目前是空的，schema 已经写好（`data/schema.md`），只差录入。每录入一局，你就多一个「可对照 meta 的个人样本」；录满 50 局，第 90 章的复盘方法就能从「凭记忆的定性复盘」升级为「对着数据的定量复盘」——你的装备选择与当日 fit 首选差多远、你的天赋与登顶局频次表差多远，全部可算。这也是 CoachView 的设计前提：AI 教练的对照分析，吃的就是结构化的 matches 数据加当日 meta 快照，素材缺失时它只能输出泛泛之谈。

## 六、方法学红线：自建分析的五条铁律

工具越顺手，出假数据越快。这五条不是从教科书抄来的美德清单，每一条背后都有一次真实事故——重复计数伪影推翻过 v1 整份报告，27 局的小样本差点把「瑶妹+骨架」误判成普通弱组合，fit-lift 伪影差点让贤者之书混进出装表。五条红线全部有真实事故背书：

1. **先去重再统计**。橱窗深分页无稳定排序键导致同局重复下发（360 条目去重后仅 120 局唯一对局），v1 的「53 局超顶级/两线垄断 85%」全部是伪影。任何基于条目级数据的统计，第一步必须是 gameTime 唯一化。要诚实记录去重代理的局限：gameTime 并非严格唯一键，毫秒碰撞理论上存在——16 组时间戳碰撞经核对属不同对局，这就是为什么最终口径是「碰撞组逐个人工核对」而不是无脑按时间戳丢弃。去重规则本身也要写进口径披露，因为不同的去重规则会产出不同的分位数（P75 从虚高的 1414 修正到真实 1293，差了 121 分）。
2. **样本量门槛**。低于 100 局的格子只配「方向性参考」（27 局的瑶妹×骨架 10.5% 是警告样本）；给出结论必须附带局数和置信区间。
3. **source 与 verified 字段强制**。所有入库数据标注来源；社区来源 `verified: false`、官方/实测 `verified: true`。没有 source 字段的 JSON 不允许进入分析链路。
4. **绝不编造数值**。查不到就写「待验证」并给出验证路径。这条红线对 AI 协作尤其关键，第 99 章整章都在讲它。判别「编造」的标准要明确：把「无改动」推断成「强度不变」是推演（合法，需标注），把「复生 4→5 张」推算出一个具体达成率数字却拿不出计算依据是编造（非法）。两者一线之隔——**有推导链的估计是分析，没有推导链的数字是虚构**。
5. **脚本可复现**。每个分析脚本产出必须带时间戳、输入文件路径和参数，让任何人（包括三个月后的你）能用同一条命令得到同一个数字。不可复现的分析等于没做。

## 对抗性审查

**攻击 1：「数据冻结之下，本章教的所有远端分析都没有增量价值——你只能吃四日快照的存量。」** 大部分成立。冻结期新增远端查询能做的只剩 explore 条件统计和 fit 时间序列两项，项目 1、2 的远端部分确实只能等解冻。但要区分「工具的价值」和「数据的价值」：本章教的是仪器，仪器的价值在数据恢复的那一刻兑现——解冻后第一天，有仪器的人 30 分钟出补丁 diff 报告，没仪器的人从零搭。历史证据是审查发现 #14：equipment-fit 未冻结这个意外，恰恰被现成的时序工具立刻转化成了痛苦面具补丁加强的发现。工具先于数据准备好，是冻结期唯一正确的姿势。

**攻击 2：「自建统计的口径会和站方口径漂移——你的 16.7% 基线和别人的 16.7% 不是一回事。」** 成立且无法根治。自建口径的自选偏差：去重规则（gameTime 唯一化 vs 站方内部键）、窗口定义（自然日 vs 滚动 7 天）、条件组合方式都可能与站方不同。缓解是**锚点对表**纪律（2.5 节的基线校验）加上一个表态：wxq-lab 的数字只在 wxq-lab 口径内互相比较，不与站方页面数字直接混用。这条要写进每个分析报告的口径披露里——v3 报告的「口径披露」小节就是这个纪律的样板。

**攻击 3：「维护成本被低估了——源站改一次响应结构，全部脚本报废。」** 成立。v260917 补丁顺带升级了数据库结构（新 key bT/c3/c4，英雄数据含 tags/card 字段），split 脚本因此暂不重跑——结构漂移是已经发生的事实而非风险。缓解是分层防御：直连解析层（最先坏）与本地分析层（`data/*.json` 格式稳定，几乎不坏）解耦，坏一层修一层；`npm run shot` 四视图截图回归可以在每次改动后一分钟内确认前端没有连带损坏。但诚实的结论是：这个项目的数据层就是脆弱的，它的可持续性建立在「每个补丁日花一小时维护」的意愿上——不愿付这个成本时，正确动作是降级到纯本地分析，而不是让脚本带病运行。

## 本章可迁移原则

> **工具的终极形态不是界面，是可复现的脚本：一个输入路径、一个输出文件、一条命令。任何你能描述清楚的分析需求，都可以拆成「采集（尊重礼貌规则）→ 落盘（带 source）→ 条件查询（先去重）→ 交叉验证（至少两种口径）」四步，而这条流水线的每一环，都比你想象地更容易用一百行脚本实现。**
