# 第八十四章 · 数据源使用指南：怎么用 wxq-lab 的每个功能

> **读完这章你能**：知道 wxq-lab 每条命令、每个数据文件、每个 API 端点、每个前端页面是干什么的，以及数据冻结期怎么安全地使用它们下结论。

---

## 一、wxq-lab 是什么：三职责与边界

wxq-lab 是私人研究工具，不是攻略站，不是模拟器。它只做三件事：

1. **复盘解析**：赛后把对局信息（文字/截图/阵容码）对照数据给出失误分析和改进结论，结构化存档；
2. **组合研究**：在棋手 × 天赋 × 棋子 × 装备 × 站位的组合空间里找当前环境的最优搭配；
3. **每日数据**：从万象棋大数据（datawxq.com）抓取真实对局统计，积累版本环境时间线。

同样重要的是它不做什么：对局内实时辅助（封号风险，且不是需求）、战斗模拟器（已明确否决）。第 98 章讲怎么在这个底座上做自定义分析，本章是使用手册——东西在哪、怎么用、哪里有坑。手册的所有内容以 2026-09-21 的实际目录与代码为准，工具迭代后以仓库为准。

三个职责各自对应一条固定工作流，全书的章节都挂在这三条流程上：

| 职责 | 触发词 | 工作流 | 数据落点 |
|---|---|---|---|
| 复盘解析 | 「复盘」 | 收集对局信息 → 结构化存档 → 对照当日 meta 快照 → 输出不超过三条失误归因与三条可执行改进 | `data/matches/` |
| 组合研究 | 「研究阵容/搭配」 | 从卡牌库取组件 → 对照最新 meta 判断环境 → 产出两三套候选（核心思路/成型回合/强弱期/克制关系/验证计划） | `data/insights/` |
| 每日数据 | `./scripts/update.sh` | 拉取 → 落盘 → 生成 summary → 与前日 diff | `data/meta/<日期>/` |

复盘流程的第四步值得强调：改进结论要具体到「第 X 回合该做什么」的颗粒度——这是复盘和感想做工的分界线，也是第 90 章复盘模板的原型。

三条流程喂的是同一个数据源优先级表（按可信度与实时性排序）：

| 优先级 | 数据源 | 内容 | 更新方式 |
|---|---|---|---|
| 1 | 万象棋大数据 API | 英雄/棋手/装备榜单、阵容排行、登顶率、6 小时趋势 | 每日 update.sh 直连 |
| 2 | 卡牌资料库（已全量入库） | 85 英雄/21 棋手/73 装备/255 天赋/6 阵营的机制数据 | 版本更新后重跑 extract+split |
| 3 | 静态 wiki（gametool.huya.com/hokc） | 技能节点、拍卖装备/天赋 | 版本更新时交叉校验 |
| 4 | 用户实拍截图 | 游戏内实时信息、复盘素材 | 用户提供，Claude 解析 |

优先级的含义：上层与下层冲突时信上层（官方统计压过 wiki），但第 4 层有特殊地位——它是唯一带段位与实战场景的素材，第 1 层的混排池数据解释不了的问题（你所在分段的真实环境）只有它答得了。

## 二、数据获取：四条管道

### 2.1 每日统计：update.sh

```bash
./scripts/update.sh              # 直连 API 拉取当日统计（秒级）→ data/meta/<日期>/
WXQ_FULL=1 ./scripts/update.sh   # 浏览器全量抓取模式（接口勘察用）
```

日常模式直连 `api.datatft.com/wzwxq/*`，产出落在 `data/meta/<日期>/`：`summary.md`（版本环境摘要，英雄榜/棋手榜/装备榜/阵容榜的表格化呈现）加 `api/` 目录下的原始端点数据。09-14 那天的快照里还有 `capture-report.md` 和 `raw/`，那是全量模式的产物——`WXQ_FULL=1` 用 playwright-core 驱动系统 Chrome，在 datawxq 页面里截获全部 JSON 响应，是做接口勘察时的工具，日常不需要也不建议天天跑（见 2.4 的礼貌规则）。

### 2.2 卡牌库重提取：版本更新后必跑

```bash
node scripts/extract-database.mjs   # 前端内嵌卡牌库 → data/raw-database.json
node scripts/split-database.mjs     # 拆分入库 → data/heroes|commanders|equipment|talents 等
```

datawxq 是 Vue SPA，静态 curl 拿不到数据，卡牌库整体打包在 `/assets/seo-*.js` 模块内——extract 脚本在站点同源的浏览器环境里 import 后导出。拆分后的规模：85 英雄（基础面板+技能+觉醒）、21 棋手（技能/秘技/专属）、73 装备（合成树+效果）、255 天赋/秘技牌、6 阵营。

触发条件是版本更新，但 v260917 之后这两个脚本没有重跑——因为 diff 显示应用层数据只有花木兰的文本过期，属外观性陈旧（09-21 报告审查发现 #17 第 8 条）。这个判断本身是工具使用规范的示范：重跑有成本，先 diff 再决定跑不跑。

### 2.3 GitHub Actions：封禁对策

现实：本机 IP 已被 `api.datatft.com` 封禁。日志（`data/meta/updates.log`）里 09-16 04:29 起出现带本机 IP 的 `code=42000 系统异常` 错误记录，此后每日抓取持续失败；封禁甚至影响 datawxq 官网在本机网络的正常浏览。对策：采集迁到 GitHub Actions，每日 08:53 自动快照，手动触发用 `gh workflow run daily-snapshot`。注意 GitHub 机房 IP 也曾被封过、一天后解封——云端 IP 不是免死金牌，只是分散了风险。

### 2.4 抓取礼貌

每日 1 次、正常 UA、遵守 robots.txt（datawxq.com 仅禁 /admin）。这不是客套：datawxq 是整个项目的单点依赖，被封一次就是几天数据盲区——09-20 的整体冻结就是活例（第六节）。抓得越勤，死得越快，这条规则的经济学理由比道德理由更硬。

### 2.5 辅助脚本地图

`scripts/` 下 update 主链之外的脚本，按命名与 09-21 报告工具链档案整理（未逐一审计的以仓库为准）：

| 脚本 | 用途 |
|---|---|
| `fetch-meta.mjs` | update.sh 的执行体：拉取各端点并在数据源异常（code=42000）时报错退出 |
| `comp-query.mjs` | 英雄×棋手等联合条件查询；整体容错+增量落盘 |
| `cmd-comp-query.mjs` | 棋手×阵容联合查询 |
| `eq-combo-query.mjs` | 装备组合查询 |
| `explore-sample.mjs` | 对局橱窗采样（20 秒 fetch 超时） |
| `hs-analysis.py` / `strength-survey.mjs` | 超顶级局与强度勘察，均已内置 gameTime 去重 |
| `meta-evolution.py` | meta 时间序列演化 |
| `explorer-recon.mjs` | explorer 接口勘察 |
| `capture.mjs` / `update-service.mjs` | 全量抓取与定时服务 |
| `dev.mjs` / `serve.mjs` | 开发数据服务器与生产服务（含 /api/datatft/* 代理） |
| `screenshot.mjs` | npm run shot 的执行体，四视图截图回归 |

这张表的读法和 4.7 节的铁律连着：分析类脚本（comp-query 系列、hs-analysis、strength-survey）是统计的唯一合法入口，界面和原始 JSON 不是。

### 3.1 目录结构（2026-09-21 实况）

| 路径 | 内容 | 更新条件 |
|---|---|---|
| `data/heroes.json` + `hero-details.json` | 85 英雄基础面板与详情（技能/觉醒） | 版本更新后重跑 split |
| `data/commanders.json` + `commander-details.json` | 21 棋手（技能/秘技/专属） | 同上 |
| `data/equipment.json` + `equipment-details.json` | 73 装备（合成树+效果） | 同上 |
| `data/talents.json` + `talent-details.json` | 255 天赋/秘技牌 | 同上 |
| `data/factions.json` | 6 阵营 | 同上 |
| `data/raw-database.json` | extract 脚本的原始导出 | 同上 |
| `data/meta/<日期>/summary.md` | 当日版本环境摘要（榜单表格） | 每日抓取 |
| `data/meta/<日期>/api/*.json` | 原始端点数据（heroes/commanders/equipment/lineups/equipment-fit/trend-hero） | 每日抓取 |
| `data/meta/<日期>/*.json` | 分析产物（comp-stats、eq-combo-stats、explore-sample 等） | 分析脚本运行时 |
| `data/meta/updates.log` | 抓取日志（成功/失败/异常明细） | 每次抓取追加 |
| `data/matches/` | 复盘记录（schema 见 data/schema.md） | 每次复盘 |
| `data/insights/` | 研究报告（含本书与 09-21 推荐） | 随研究产出 |

现有快照：2026-09-14、09-15、09-20、09-21 四天——这就是全部数据底座（114 万局聚合 + 54 万局装备 fit + 240 局橱窗采样）的时间范围。在这之外的任何日期，数据不存在。

### 3.2 四条铁律

1. **data/ 下的 JSON 是唯一事实源**：先更新数据，再下结论——顺序不能反。
2. **所有入库数据必须带 source 字段**：社区来源标 `verified: false`，官方或实测标 `verified: true`。
3. **绝不编造数值**：查不到就写查不到，列为待验证项，给出验证路径。本书每一章末尾的数据来源行就是这条规范的执行样本。
4. **先看 `data/meta/updates.log` 再下结论**：日志记录了每次抓取的成败与异常——09-16 04:26 那条「heroesLeft: 85」（85 个英雄一夜全部离榜）就是封禁降临的第一现场，比任何事后分析都早。

### 3.3 口径标注规范

insights 目录里的研究产出，引用时遵循两条格式约定：

- **引用必带口径**：「09-20 冻结口径」「去重后 12 局唯一对局」「假设值待实测替换」这类后缀不是装饰，是数字的一部分——去掉后缀的引用视同篡改。
- **推翻不删除**：v1 报告被证伪后仍保留在目录里，头部加修订声明说明哪部分被推翻、为什么。错误分析的价值在于它是校准样本——删掉它，第 82 章的「推演校准曲线」就失去了历史数据。

## 四、四个 API 端点逐一详解

端点均为已抓包验证（2026-09-14），公开无需鉴权。

### 4.1 总表

| 端点 | 方法 | 作用 | 关键坑 |
|---|---|---|---|
| `/wzwxq/rankings/{heroes\|commanders\|equipment}?time=7&version=v1` | GET | 英雄/棋手/装备榜单（登顶率/前三率/均次/样本量） | time=7 是滚动窗口，补丁会污染窗口 |
| `/wzwxq/ranking-trends?type={hero\|commander\|item}&time=7&version=v1` | GET | 6 小时粒度趋势序列 | 冻结前序列止于 09-16 |
| `/wzwxq/lineups/search` | POST | 阵容搜索（含英雄/装备名称映射） | heroId 等过滤参数未生效 |
| `/wzwxq/equipment-fit` | POST | 72 装备 × 85 英雄的 winRateLift 矩阵 | fit-lift 有选择语境伪影 |

### 4.2 rankings：一切分析的起点

榜单返回英雄（含平均等级）、棋手、装备三张表的登顶率、前三率、平均名次与样本量。两个解读要点：样本量过滤（summary 默认只呈现 ≥1000 场的行，低样本行的噪声极大）；滚动窗口的补丁污染——time=7 在补丁日后几天内混合了新旧两个版本的数据（第 82 章的去卷积就是为解决这个问题而做的）。

### 4.3 ranking-trends：时点判别的关键材料

6 小时一个点的趋势序列，是「补丁论 vs 学习论」这类时点判别的唯一数据来源——v260917 的判别依据就是崩盘台阶与 09-17 精确重合。注意冻结前最后一个有效序列的 28 个 6 小时点全部落在 09-16 之前：趋势数据对「补丁后发生了什么」目前一片空白。

### 4.4 lineups/search：能用，但过滤要自己做

阵容搜索可用，返回里含英雄/装备名称映射，阵容排行数据由此而来。坑：`heroId` 等过滤参数发过去会被服务端忽略——想按英雄过滤阵容，拿到结果后在自己的代码里过滤，不要指望参数。

### 4.5 equipment-fit：唯一活水，但证据等级最低

装备 × 英雄的登顶率提升（winRateLift）矩阵，60 万场次量级；冻结期内它从 43 万局长到 54 万局，是全数据源唯一还在更新的表——第 82 章的「痛苦面具被补丁加强」发现，就是靠这条活水的四日 lift 序列（-8.3pp 转正 +9.6pp）抓到的。但 fit-lift 的证据等级是三种口径里最低的：+30pp 的贤者之书 lift 被联合条件查询证伪为选择语境伪影（出贤者之书的露娜多处于法师体系局，体系强度记到了装备头上）。**证据等级：联合条件查询 > fit-lift > 极限局单局样本，三者矛盾时信前者。**

### 4.6 无 CORS：浏览器一律走代理

第三方 API 不带 CORS 头，浏览器直接请求会被拦。前端一律走 `serve.mjs` 的 `/api/datatft/*` 代理（开发模式由 Vite proxy 转发）。这意味着浏览器端的分析产物都经过本地服务器，直接把 API 地址贴进浏览器控制台是行不通的。代理层还有个附带好处：抓取策略（频率、UA、缓存）收口在一个地方，2.4 节的礼貌规则只需要实现一次。

### 4.7 方法论铁律：先去重再统计

explore 橱窗曾被发现严重重复计数：360 条采样条目去重后仅 120 局唯一对局（深分页无稳定排序键的典型病症）。09-21 报告 v1 的「53 局超顶级、两线垄断 85%」全部由此伪影，事后推翻重写。去重口径是 gameTime 唯一化（非严格唯一键，作为代理足够可靠），`hs-analysis.py` 与 `strength-survey.mjs` 已内置。任何以「局」为单位的统计，先问去重口径——这条铁律是用一次全文重写的代价换来的。

### 4.8 串起来：一个问题的完整数据路径

以「露娜第三件装备出什么」为例（09-21 报告真实处理过的问题），正确的数据路径是四层：

1. **rankings** 拿露娜的全池基线（登顶 24.3%）；
2. **equipment-fit** 拿候选装备的 lift 排序（贤者之书 lift 增强至 +30.2pp——注意这只是候选名单）；
3. **联合条件查询**（comp-query.mjs）逐件裁决：魔律之刃 39.7% 登顶断层第一、聚灵水晶 35.3%、贤者之书 27.6%——lift 的排序被部分推翻；
4. **交叉验证**：四日时间序列确认魔律之刃 lift 稳定 +27~28pp、去重后极限局里露娜 7 局带三装且出装横跨八种——结论「魔律+聚灵固定，第三件灵活实验位」。

四层的证据等级逐层提高，结论逐层收窄。跳过中间层直接下结论的做法（只看第 2 层就推荐贤者之书——v2 报告真的这么错过）都会被后一层打脸。这条路径是全工具链的缩影：**rankings 定基线，fit 给候选，联合查询做裁决，时间序列与极限局做复核。**

## 五、前端界面逐页说明

以 `ui/src/views/` 实际文件为准，十个视图各管一件事。启动方式：`npm run ui`（serve.mjs 供 dist/ 与 /data，浏览器开 `localhost:5177`）；开发用 `npm run dev`（:5178 数据服务器 + :5173 Vite 热更新双进程）；改完界面跑 `npm run shot` 做四视图截图回归。

| 视图 | 一句话定位 | 什么时候打开 |
|---|---|---|
| MetaView | 环境页：夜空横幅 + 英雄/棋手/装备榜单 + 热门阵容 + 连通数据条 | 每天第一个打开的页面，版本环境速览 |
| CodexView | 卡牌图鉴：85 英雄/21 棋手/73 装备/255 天赋查询 | 查任何单位的面板、技能文本、觉醒 |
| HeroDetailView | 英雄详情 /hero/:id：装备搭配+趋势+热门阵容位置+常见搭档+我的记录 | 定主 C 之前、复盘装备分配时 |
| EquipmentFitView | 装备搭配：winRateLift 排序矩阵 | 选秀前查「这件散件给谁」——记得 4.5 节的证据等级 |
| WorkshopView | 阵容工坊：组合研究 | 产出候选搭配（组合研究流程的工具侧） |
| LogView | 对局复盘记录（localStorage 存档，schema 见 data/schema.md） | 每局赛后 |
| CoachView | 教练分析：09-21 报告这类产物的生成入口 | 阶段性复盘与研究 |
| ExplorerView | 对局探索：橱窗数据勘察 | 查极限局样本——必须用去重后口径（4.7 节） |
| TierView | 强度梯度：第 36 章那张表的界面形态 | 决定下一个升级节点时 |
| FactionsView | 阵营：6 阵营羁绊数据 | 凑羁绊（第 45 章） |

环境页的 three.js 悬浮卡牌（Hero3D.vue）是视觉主体，减动效设置下自动降级为静帧——工具的审美部分不影响任何数据路径。使用上最常见的错误是拿着 EquipmentFitView 的排序直接当出装结论——把 4.5 节的证据等级再读一遍再用。

十个视图组成了三条典型使用路线，对齐第一节的三职责：

1. **赛前准备路线**：MetaView 看环境 → TierView 定升级路线 → HeroDetailView/EquipmentFitView 细化出装 → WorkshopView 产候选搭配。
2. **赛后复盘路线**：LogView 记录对局 → 对照 MetaView 当期榜单 → CoachView 出复盘结论 → 结论回写 LogView。
3. **版本研究路线**：update.sh 落新数据 → ExplorerView 勘察新对局样本（先去重）→ 脚本做条件统计 → 结论写进 insights。

路线的价值在于固定顺序：数据浏览永远在统计之前、统计永远在结论之前——顺序颠倒是工具使用中最常见的自我欺骗形态。三条路线走完一轮的频率建议：赛前路线每次坐店前、复盘路线每局赛后、研究路线每个补丁周期至少一次——工具的价值在节奏里，不在收藏夹里。

## 六、数据冻结期的使用纪律（当前状态）

### 6.1 现状

09-20 起聚合/榜单/趋势/橱窗整体冻结：聚合基线样本 1,137,509 两日全等；对局橱窗停在 09-16 23:38-23:57 的 17 分钟窗口；仅 lineups 与 equipment-fit 有活动。数据底座是 09-14/15/20/21 四日快照。这个现状同时是本书全部数字的时效锚：引用任何一章的数据，效力都不超过解冻后的第一次复核（见 6.2 第 4 条）。

### 6.2 四条纪律

1. **日期意识**：引用任何数字先报快照日期（「09-20 冻结口径」）。过期数据不如没有数据——它会让你的结论显得有据，而依据已经死了。
2. **冻结字段与活动字段分开对待**：lineups 和 equipment-fit 还在动，可以继续做时间序列；聚合与榜单是照片不是直播，不能当「当前环境」引用。两者的混用是冻结期最隐蔽的错误——一张 09-20 的榜单配上 09-21 的 fit 数据，看起来像「最新环境」，实际是两个时间点的缝合。
3. **先读 updates.log**：解冻没有公告，日志里第一条成功记录就是解冻时刻——任何分析之前先确认你引用的数据是活的。
4. **解冻后 24 小时内重跑全部分析**：这是进度追踪里挂号的触发器。盲区期的所有结论（第 82 章）都等着这一刻复核——重跑的不是数字，是过去所有决策的有效性检验，优先级高于任何新分析。

冻结期不等于无数据期——它把工具的用法从「看当前环境」切换为「用历史底座 + 唯一活水做推断」。第 82 章的补丁推演、本书引用的全部条件统计，都是这么来的。

### 6.3 冻结期还能做的五件事

1. **盯 lineups 与 equipment-fit 两条活水**：它们还在长样本，时间序列分析照常可做（第 82 章的痛苦面具发现即产物）。
2. **复盘回流**：matches/ 的复盘记录不依赖外部数据源，冻结期恰好是把个人对局库补厚的窗口——外部数据停了，第一手数据没停。
3. **卡牌库精读**：85 英雄/255 天赋的机制细节在本地 JSON 里，版本理解（第 97 章）的机制功课不依赖榜单。
4. **补丁档案与推演校准**：第 82 章的档案制度在冻结期照常运转，且冻结期的推演偏差样本更珍贵。
5. **解冻演练**：预先写好解冻后要重跑的分析清单，数据一活就执行——解冻后 24 小时是黄金复核窗口，别花在「想该跑什么」上。

## 对抗性审查

**攻击 1：工具数据没有段位维度——114 万局全是混排池，对本书读者（王者 200+ 到巅峰）的适用性全靠代理。**

成立，这是全数据源最大的结构性缺陷。所有结论都要打「混排折扣」：条件统计回答的是「大体池里谁强」，不直接回答「巅峰段谁强」。项目用「唯一超顶级对局（总等级 ≥2000）」做高段位代理，但去重后样本仅 12 局，连报告自己都只把它当方向性证据。工具迭代方向第一位就是段位维度——若服务端哪天下发段位字段，本书一半结论需要重新标定。

**攻击 2：代理口径还有第二层问题——超顶级代理高段位，且无逐回合数据。**

成立且不可修复。没有逐回合胜率增量，「凑齐骨架 → 登顶」的边际贡献无法从幸存者偏差中分离（09-21 报告红队攻击 1，全数据源条件统计共有的缺陷）。缓解方式不是更好的统计，是换仪器：你打的 10 局验证局是唯一干净的因果仪器，工具数据负责提假设，实测负责裁决。

**攻击 3：工具自身的输出层可能仍展示未去重口径——工具本身就是陷阱的一部分。**

半成立。ExplorerView 等界面底层的数据存在重复计数病史，分析脚本已内置 gameTime 去重，但界面呈现与脚本口径未必一致。使用纪律因此写成硬规则：界面用来浏览，统计一律走脚本；任何以局为单位的数字先问去重口径。这条纪律失效过一次（v1 报告重写事件），不能假设它不会再失效。

**攻击 4：单点依赖。** datawxq 封禁加冻结已经证明这个架构的脆弱性：一个第三方站点的态度决定整个项目的数据命脉。承认，当前没有备选数据源。缓解只有两个：卡牌库已全量本地化（这部分不依赖网络，是永久资产）；Actions 多点采集分散封禁风险。真正的对冲是保持「绝不编造数值」的纪律——数据缺席时说缺席，工具的可信度比工具的覆盖率值钱。反过来说，这次冻结也算一次压力测试：第 82 章证明盲区期内靠 diff 加推演加体感分层，决策链没有断。

**攻击 5（自我审查）：本章的命令与视图清单会过时。** 成立。工具在迭代（视图可能增删、脚本可能重构），本章所有路径与命令以 2026-09-21 的仓库实况为准。这不是缺陷是事实：手册类内容的有效期天然短于原理类内容，第 98 章讲的是不变的数据思维，本章讲的是会变的工具形态——两者读法不同。

## 本章可迁移原则

> **工具的产出上限，等于你对它口径的理解下限。每一个数字都要能回答三件事：什么时候抓的、多少样本、什么口径——回答不了就不要用它做决策。数据是唯一事实源，但日期是事实源的事实源；界面用来浏览，脚本用来统计，实测用来裁决。**
