# 第一百九十一章 · 数据采集的完整管道：从 API 到分析

> **读完这章你能**：画出 wxq-lab 从数据源到结论的三层管道图——六个统计端点、一份快照纪律、七台分析脚本各在哪一层；说清 fetch-meta 的四道防线分别在拦什么、42000 伪装成 HTTP 200 为什么要专门防；看懂 09-16 到 09-22 这七天的管道事故记录，把「冻结」「封禁」「窗口异常」三种故障从日志特征上区分开；拿到一张每天三分钟、每次补丁前必查的管道维护清单。

## 一、管道全景：三层结构，一条纪律

前面所有章节用过的每一个数字——三核 46.6%、魔律之刃 +28.5pp、孙小宾 72.5%、去卷积真值表的每一个格子——都不是从天上掉下来的。它们全部出自同一套管道：**数据源进快照，快照进分析，分析出结论，结论回炉复盘**。本章把这套管道完整拆开。目的有两个：一是让你能自己维护它——管道断一天，第 196 章的去卷积就断一次粮；二是让你知道每个数字的出生证明——一个说不清来源的数字，不值得用来押段位。

三层结构从下往上：

| 层 | 内容 | 载体 | 更新节奏 |
|---|---|---|---|
| 采集层 | 六个 API 端点 + 浏览器全量抓取 | `scripts/fetch-meta.mjs`、`scripts/capture.mjs` | 每日一次（08:53 定时） |
| 事实层 | 卡牌库 + 每日快照 + 对局记录 | `data/heroes.json` 等、`data/meta/<日期>/`、`data/matches/` | 每日落袋 / 版本更新时重提取 |
| 分析层 | 条件查询、样本分析、跨日对照 | `comp-query.mjs` 等 5 个查询脚本 + 2 个 Python 分析器 | 按需，每次结论前必跑 |

**一条纪律贯穿三层：`data/` 下的 JSON 是唯一事实源。** 结论可以写在任何地方，但数字必须能回溯到 `data/` 里的某个文件、某个字段。这条纪律的代价是麻烦——每个数字都要落盘、要带 `source` 字段、社区来源标 `verified: false`；收益是第 197 章的红队攻击永远有案可查：攻击一个结论，就是攻击一份可以重新加载的原始数据，而不是攻击一段记忆。

先说清楚数据源是什么。万象棋大数据（datawxq.com）是一个 Vue SPA——静态 curl 拿到的只有一个空壳 HTML，数据全部是浏览器里异步请求的。但它的后端 API 是公开无鉴权的，2026-09-14 上线当天抓包确认了六个端点。这就是整个采集层的第一原则：**直连 API，不渲染页面**。直连一次请求不到半秒（09-15 的快照任务全程 441 毫秒），浏览器模式一次要几十秒——所以直连是日常，浏览器是勘察。

## 二、第一层：六个端点与它们各自的角色

`fetch-meta.mjs` 每天按固定顺序拉六个端点，全部落在 `data/meta/<日期>/api/` 下：

| # | 端点 | 方法 | 产出文件 | 回答的问题 |
|---|---|---|---|---|
| 1 | `rankings/heroes?time=7&version=v1` | GET | `api/heroes.json` | 每个英雄的登顶率/前三率/均次/平均等级（7 天窗口） |
| 2 | `rankings/commanders` | GET | `api/commanders.json` | 21 个棋手的同口径榜单 |
| 3 | `rankings/equipment` | GET | `api/equipment.json` | 装备榜 + 全局基线（`base.count` 就是窗口总局数） |
| 4 | `ranking-trends?type=hero&time=7` | GET | `api/trend-hero.json` | 6 小时粒度的趋势序列（第 195 章的原料） |
| 5 | `equipment-fit` | POST `{}` | `api/equipment-fit.json` | 72 装备 × 85 英雄的 winRateLift 矩阵（第 193 章的原料） |
| 6 | `lineups/search?page=1&pageSize=12` | GET，失败转 POST | `api/lineups.json` | 热门阵容榜（含英雄/装备名称映射） |

先把响应字段钉死，因为后面所有章节的数字都从这几个字段里来。英雄榜每行的字段是 `id`、`count`（样本局数）、`firstRate`（登顶率）、`top3Rate`（前三率）、`avgPlacement`（平均名次）、`avgLevel`（平均等级）；棋手榜同名次字段但无 `avgLevel`；装备榜的 `base` 字段带出全窗口总局数。全局基线就藏在装备榜的 `base` 里：以 09-21/09-22 的快照为例，`count` = 1,137,509 局，登顶率 16.67%、前三率 50.01%、平均名次 3.4996——**登顶 16.7%（1/6 恒定）、前三 50%、均次 3.50** 这组贯穿全书的基准数，出处就是这三个字段。每个英雄的登顶率都要放在这把尺子上读：26.0% 的太乙真人是 +9.3pp，9.4% 的朵莉亚是 −7.3pp，没有基线，榜单就是一列没有单位的数。

三个细节值得停一下。**其一，id 要自己翻译。** 英雄榜和装备榜的 `id` 是数字（英雄 5141、装备 643703 这种），API 不回名字。翻译靠本地卡牌库：`fetch-meta` 生成摘要前，先读 `data/heroes.json` 建一张 id→名字的映射表，翻译不出来就老老实实写 `id:xxxx`——绝不猜。装备的映射更深一层，要把 `equipment-details.json` 里的 `previewCards` 也并进去，否则成装名字对不上。**其二，第七个端点不在每日任务里。** `explore`（POST 条件查询）是分析层的工具，礼貌成本高（第 192 章专章讲），所以它不进每日快照，按需调用。**其三，`time=7` 是窗口参数。** 所有端点默认 7 天滚动窗口——这个「7」就是第 181 章数据盲区和第 196 章去卷积的物理来源。

每日任务之外还有浏览器全量模式：`WXQ_FULL=1 ./scripts/update.sh` 走 `capture.mjs`，用 playwright-core 驱动系统 Chrome 渲染页面，截获页面发出的**全部** JSON。它的用途不是日常更新，是接口勘察——2026-09-14 上线当天摸清六个端点、后来逆向 explore 的 filters 结构（第 192 章），用的都是这个模式。日常秒级直连、勘察才开浏览器，这个分工不要倒过来。

## 三、fetch-meta 的四道防线

一个每天无人值守跑定时任务的脚本，核心不是「拉数据」，是「拉坏了怎么办」。`fetch-meta.mjs` 有四道防线，每一道都对应一种真实发生过的故障。

**防线一：code 校验，防「伪装成成功的失败」。** 这是最反直觉的一条。数据源限流或出错时，返回的是 **HTTP 200 + JSON 体里 `code: 42000`**，message 写着「系统异常，请联系站长协助处理~，117.62.245.233」。如果你只看 HTTP 状态码，会把一个错误体当快照存进盘里——然后用一份毒数据覆盖掉前一天的好数据。所以 `pull()` 函数在写盘前强制校验 `json.code !== 1 || json.data == null` 就抛错，校验不过一个字节都不落盘。09-16 当天日志里连续三条 42000 失败记录，但 `data/meta/2026-09-16/` 目录根本不存在——防线起效的样子就是「什么都没留下」。

**防线二：延迟建目录，防空壳快照。** 目录是在第一份数据校验通过后才 `mkdir` 的。为什么顺序不能反？因为 UI 会把 `data/meta/` 下字典序最新的目录当最新快照——一个空壳目录会让前端把「没有数据」当成「今天的数据就是没有」。文件系统的小礼仪，下游app的命。

**防线三：固定 UA + 每日一次。** UA 是 `wxq-lab/0.1 (personal research, 1 req/day)`，主动亮明身份和频率。这不是 decoration——第 197 章会讲，这个数据源对高频请求的真实惩罚是 IP 级封禁，09-16 和 09-21 的日志里都留下了证据（第五节拆解）。礼貌不是道德姿态，是管道的可用性预算。

**防线四：updates.log 的 diff 摘要。** 每次运行追加一行 JSON：时间、耗时、成败、以及与前一日的对照摘要（`heroesUp`/`heroesDown`/`heroesEntered`/`heroesLeft`、阵容进出）。它已经抓到过一次诡异拉取：09-16 04:26 那次任务显示成功，但 diff 写着 **`heroesLeft: 85`——全部 85 个英雄「离榜」**。榜单不会一夜清空，这只能说明那次拉回的数据是空的或者结构变了。HTTP 200、code 正常、文件也写了，但 diff 摘要一眼 exposes 它。教训：**落盘校验的最后一道，永远是常识对账**——「数字合不合理」比「请求成没成功」更接近真相。

## 四、快照纪律：为什么必须每日落袋

管道里最值钱的不是任何一段代码，是一个近乎无聊的习惯：**每天雷打不动把快照存进 `data/meta/<日期>/`，哪怕那天你一局都不打。** 三层理由。

**第一层：为下一个补丁预付干净基线。** 去卷积公式 `r_post = (W21 − 0.233 × W15) / 0.767` 里，W15 是补丁日前最后一份干净快照。09-15 那份快照（七天天天在补丁前，窗口总量 705,536 局）之所以能当 W15 用，只因为它在补丁来临前已经落袋。第 182 章的结论说得更狠：补丁来的那天，你手里有没有昨天的干净数据，决定了你三天后能不能算出真值——快照不是囤积癖，是保险费。

**第二层：冻结期里它是唯一的历史。** 09-17 补丁日到 09-19，管道三天颗粒无收（下一节拆原因）。这三天里你唯一能回答「补丁前世界长什么样」的依据，就是 09-14/09-15 两份快照。历史快照连续可查，第 195 章的时间序列和第 199 章的 meta 演进积累才成立——断掉的窗口没有任何办法事后补录，API 不供应历史。

**第三层：双日 diff 是免费的完整性审计。** 第 200 章的基础设施审计能发现「聚合跨日不翻转」，前提是 09-21 和 09-22 两份快照都在手上——两份逐行相同（窗口总量同为 1,137,509），冻结才现形。只落一份，你永远不知道榜单今天是活的还是死的。

执行载体是定时任务：GitHub Actions 每天 08:53 跑一次 `update.sh`（updates.log 里 09-16 08:53:47 的失败记录就是它留下的）。本地的手工跑法：`./scripts/update.sh [日期]`。纪律只有一条：**定时任务是主，手工是补——发现当天没落袋，24 小时内手工补上，并在 log 里注明补跑。** 解冻之后还有一个配套动作（第 184 章引用过）：解冻后 24 小时内重跑全部关键查询（comp-query、cmd-comp-query、eq-combo-query），复核冻结期间做出的每个结论——该降级的降级、该作废的作废。

## 五、冻结、封禁与窗口异常：一次完整的基础设施审计

09-16 到 09-22 这七天，管道把三种故障各得了一遍。把它们的日志特征分开记，下次你遇到时三十秒内就能定性。

**故障一：限流与封禁（42000 族）。** 日志特征是 HTTP 200 + `code=42000` + message 带 IP 地址。09-16 04:29、04:30、08:53 三连败，09-21 07:12 双败——注意 09-21 当天 05:33 那次是成功的，失败的是**同日的后续请求**。这坐实了限流模型：按 IP 计频，成功一次后当天再打就容易触发。所以操作纪律是「**每日成功一次即停，失败后冷却数小时再试，绝不连续重试**」——连续重试不是修复，是把临时限流打成永久封禁。09-16 到 09-19 的数据真空就是这么来的：补丁日前后源站本身不稳，叠加限流，管道冻结了四天。

**故障二：聚合冻结（跨日不翻转）。** 09-21 与 09-22 两份快照，英雄榜逐行相同——太乙真人都是 394,864 场 26.0%，窗口总量都是 1,137,509。7 天滚动窗口理论上每天该挪一格，两份完全相同说明**聚合统计面在这两日之间没有更新**。更深一层的证据来自 trend 接口的自报字段：09-22 抓取的 `trend-hero.json` 里，`generatedAt` 是 09-22 02:45，而窗口端点 `endExclusive` 停在 **2026-09-17T00:00Z（北京 09-17 08:00）**——恰是补丁日清晨。也就是说，补丁后那几天，统计面的窗口端点被钉在补丁时刻附近没有推进，直到 09-20 之后才恢复滚动。**读数前先核对时效**：`generatedAt` 与 `endExclusive` 的差值就是这份数据的「新鲜度」，差值超过 24 小时的快照，只能用于历史对照，不能用于「当前环境」判断。

**故障三：窗口异常（各统计面生命周期不同步）。** fit 矩阵的样本量序列：09-15 是 700,976，09-20 掉到 430,219，09-21 回到 542,089，09-22 涨到 641,965。补丁日前后从 70 万掉到 43 万——**fit 面的窗口在补丁日被重置过**，之后作为全数据源唯一确认还在更新的统计面（第 183 章叫它「盲区里唯一的活水」）持续回涨。这件事有两个推论：其一，fit 的跨日数字不能与聚合榜单直接混算——两个面窗口不同步；其二，fit 样本量是个免费的「心跳监测器」，管道整体死活不确定时，看 fit 涨没涨就知道统计面还活着没有。

**故障四（结构性，非性能）：橱窗重复。** explore 接口的对局橱窗在深分页时会重复返回同一局——09-21 的对抗性审查实测，240 条橱窗记录去重后只剩 114 局唯一对局，接近一半是重复计数。这不是某天的故障，是接口的固有行为，任何基于橱窗明细的统计（第 192 章的 explore-sample、`hs-analysis.py`）都必须先去重：去重键用 `gameTime + 阵容签名`（英雄 id 排序元组），防深分页重复，也防不同对局的时间戳碰撞误合并。

## 六、第二层：卡牌库与对局记录

快照回答「环境怎么样」，但「环境里的东西叫什么、你打得多好」要靠事实层的另外两块。

**卡牌库：版本更新时重提取。** 85 英雄、21 棋手、73 装备、255 天赋的完整资料，整体打包在 datawxq 站点的一个 `/assets/seo-*.js` 模块里。`extract-database.mjs` 的做法是开一个站点同源的浏览器环境，import 这个模块后导出成 `data/raw-database.json`；`split-database.mjs` 再拆成 `heroes/commanders/equipment/talents.json` 等入库文件。为什么绕这一道？因为 SPA 的数据不在 HTML 里，直连 API 又只给统计不给资料——卡牌资料只能从它自己的前端模块里取。**每次版本更新后都要重跑这一对脚本**：v260917 补丁的花木兰数值、嬴律重做内容，就是靠重提取落进库里的。入库纪律照旧：所有条目带 `source` 与 `verified` 字段，wiki 类来源标 `verified: false`，官方/实测标 `true`。

**对局记录：复盘的原料。** `data/matches/YYYY-MM-DD-<n>.json`，schema 在 `data/schema.md`：名次、棋手、最终阵容（英雄+等级+装备）、关键天赋、关键决策点、对手名单（`opponents` 字段——第 171 章的五张对手卡就写在这里）、结论与行动项。录入有两条纪律。**其一，赛后立刻写，超过一小时就开始失真**——你能记住的是「第 9 回合没舍得升人口」，记不住的是当时的能量精确值和商店里刷过什么；记不准的字段宁可留空，也不要编一个像样的数——这正是项目「绝不编造数值」铁律在个人记录上的执行。**其二，每条记录必须带结论字段（`conclusions`）和行动字段（`actions`）**，第 180 章的复盘模板就是按这两个字段的出口设计的：只记过程不下结论的记录是流水账，三个月后它既不能喂第 194 章的个人矩阵，也不能喂第 199 章的更新系统。它的角色在第 200 章的闭环里说得很清楚：全池统计告诉你孙小宾在谁手里是 72.5%，你的个人记录告诉你「你」在哪套体系上兑现了多少——**地图与足迹的关系**（第 194 章的个人矩阵就靠它喂养）。

**服务层：代理与端口。** 第三方 API 没有 CORS 头，浏览器直接 fetch 会被拦，所以 `serve.mjs` 在 5177 端口供 `dist/` + `/data`，并把 `/api/datatft/*` 反代到真实 API；开发时由 Vite proxy 转发。这层与数据无关，但它决定了「改数据 → 刷新页面看到新数据」这条反馈回路是否通畅——UI 把 `data/meta/` 最新目录当快照，所以快照目录的完整性（防线二）直接决定 UI 显示对不对。

## 七、第三层：从原始 JSON 到结论

分析层是五台查询脚本加两台分析器，全部按需运行、全部带同一套礼貌约束（页间/查询间 `sleep 1.5s`，遇 42000 立即中止且当日不再重试），全部增量落盘（每查完一条就 flush，中途被限流也保住已得数据）：

| 脚本 | 查什么 | 产出 | 详拆章节 |
|---|---|---|---|
| `comp-query.mjs` | 11 套候选阵容的 AND 条件统计 | `comp-stats.json` | 第 192 章 |
| `cmd-comp-query.mjs` | 棋手 × 骨架联合条件 | `cmd-comp-stats.json` | 第 194 章 |
| `eq-combo-query.mjs` | 英雄 × 单件装备联合条件 | `eq-combo-stats.json` | 第 193 章 |
| `explore-sample.mjs` | 对局橱窗逐页采样（默认 30 页 × 12 条） | `explore-sample.json` | 第 192 章 |
| `explorer-recon.mjs` | 浏览器逆向 explore 的请求结构 | `/tmp/explore_req*.json` | 第 192 章 |
| `hs-analysis.py` | 高强度样本分析：去重、Jaccard≥0.6 原型聚类、原型胜率 | 终端报告 | 第 192 章 |
| `meta-evolution.py` | 跨快照多日对照（英雄/棋手/阵容） | 终端表格 | 第 195 章 |

分工原则：**条件查询回答「这个组合的平均表现」，样本分析回答「这个组合在高强度局里长什么样」。** 两者口径不同（前者是聚合统计，后者是橱窗明细 + 去重 + 强度阈值过滤，high=1200/ top=1600 总等级），结论不要混用——第 197 章抓过正面的例子：橱窗小样本让人误判镜不玩太乙真人，条件查询的 471 局把结论顶了回来。

## 八、常见错误

1. **只看 HTTP 状态码判断成败。** 42000 的错误体是 200 包装的，不校验 `code` 就落盘，等于给好数据埋雷。这是四道防线里的第一道，也是唯一一道「犯了就污染历史数据」的错。
2. **失败后立即重试。** 限流是按 IP 计频的，立即重试大概率触发升级惩罚。09-16 的三连败里，至少后两次是重试烧出来的。正确动作：冷却、次日定时任务自然会再来。
3. **同日重复快照不标注。** 09-21 当天成功过 05:33 一次，失败过 07:12 两次——如果你手工补跑又成功了一次，目录里就有两份数据。覆盖前先 diff：聚合面在一天内基本不变，变了才值得注意，把「哪份是正式快照」定死（以定时任务那份为准）。
4. **用名字查 API。** API 认 id 不认名字，名字到 id 的映射必须走本地卡牌库，映射不到就显式报错，禁止猜测性 fallback——猜错一个 id，条件查询就在统计一个不存在的阵容。
5. **拿橱窗明细当全量。** 橱窗是抽样（还有深分页重复），`base.count` 才是聚合口径的样本数。任何「n=」必须写清来自哪个口径：聚合 base、fit 矩阵、还是去重后的橱窗。
6. **忽视时效字段。** `generatedAt` 和 `endExclusive` 是每份接口数据的出生时间和统计截止时间。窗口冻结期间，一份「今天抓的」数据统计的可能是「补丁日清晨为止」的世界——不查 `endExclusive`，你会把旧世界当成新环境。

## 九、落到执行：本章的决策出口

**每日清单（三分钟）：**
1. 确认 08:53 定时任务落袋：`data/meta/<今天>/api/` 下六个文件齐全，`summary.md` 生成。
2. 扫一眼 `updates.log` 最后一行：`ok:true`？diff 摘要有没有 `heroesLeft` 全离榜这类常识性异常？
3. 快照齐全则当日不再请求 API；失败则记入待办，冷却后手工补跑一次。

**故障处置表（贴在管道旁边）：**

| 症状 | 定性 | 动作 |
|---|---|---|
| HTTP 200 + code 42000 | 限流/封禁 | 停手，冷却数小时；次日定时任务重试；绝不连发 |
| 快照成功但 diff 全体离榜 | 数据源异常拉取 | 该快照标记可疑，用昨日快照顶替当天分析 |
| 双日快照逐行相同 | 聚合冻结 | 改用方向与排序读数，等翻转；fit 心跳确认面是否存活 |
| `endExclusive` 滞后 >24h | 窗口滞后 | 数据只做历史对照，不做「当前环境」判断 |
| 橱窗深分页重复 | 结构性行为 | 采样后按 `gameTime+阵容签名` 去重再统计 |

**补丁前检查单（每次公告日过一遍）：**
- 最近 7 天快照连续无缺口？缺口在补丁前，去卷积的基线就没了。
- 卡牌库是否需要重提取（等补丁上线后跑 extract + split）？
- 三个查询脚本的关键查询清单是否已固化（补丁后 24 小时内重跑用）？

**工具清单（第 196 章要求贴在去卷积表格旁边的就是这张）：** 采集层 `update.sh`（日常）/ `capture.mjs`（勘察）；事实层 `data/meta/<日期>/`、`data/*.json`、`data/matches/`；分析层 `comp-query` / `cmd-comp-query` / `eq-combo-query` / `explore-sample` + `hs-analysis.py` / `meta-evolution.py`。

> **本章可迁移原则：**
> 1. **管道的价值不在采集，在拒绝采集。** 校验不过就一个字节不落盘的系统，比什么都能存的系统可信一个数量级——数据工程的全部难点在「坏数据长得很像好数据」。
> 2. **为断供日备份，而不是为使用日备份。** 干净基线的价值在它失效之后才出现；任何「现在用不上」的历史快照，都是在给未来的推演预付本金。
> 3. **基础设施要定期审计，且审计要有日志可查。** 冻结、限流、重复计数这类问题，靠的不是更聪明的算法，是「把两次运行放在一起对比」这个最原始的动作——前提是两次运行都被完整记录了。
