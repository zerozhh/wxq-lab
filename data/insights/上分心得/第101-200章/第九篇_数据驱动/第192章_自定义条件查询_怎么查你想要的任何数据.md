# 第一百九十二章 · 自定义条件查询：怎么查你想要的任何数据

> **读完这章你能**：徒手构造一个 explore 查询体——filters、exclusions、operator、分页七个字段各填什么、错什么会静默失效；复述这套参数是怎么用 playwright 点着官网界面逆向出来的，以及下次接口改版时怎么重做一遍；用「聚合 base 归统计、橱窗明细归样本」的口径纪律读响应，不被 240 条里只有 114 局唯一对局的重复计数骗到；设计一个查询前先过样本量预算，而不是查完才发现条件把样本筛没了。

## 一、榜单回答不了的问题：为什么需要条件查询

每日快照的三个榜单（英雄/棋手/装备）有一个共同的先天缺陷：**它们都是边际统计**。「孙悟空登顶 25.10%」的意思是「所有包含孙悟空的对局的平均登顶率」——这些对局里，有人拿他当主 C 配齐魔律之刃，有人拿他凑羁绊两星挂件，有人 30 名开外的水平硬玩，全部搅在一起。边际统计回答「这个英雄热不热、平均强不强」，回答不了你真正想问的问题：**「在特定条件下，表现是多少？」**

条件查询是这游戏里你能拿到的、最接近因果推断的观测工具。它把「对局池」按你的条件切片，然后对切片内的对局重新算一遍登顶率/前三率/均次。三核骨架 46.62% 这个数字的分量与边际榜完全不同：它说的是「露娜、孙悟空、太乙真人**同时在场**的对局」，把「拿了露娜但没凑齐骨架」的局全部剔掉了——条件越贴近你实际要执行的体系，数字对你的参考价值越高。第 194 章的棋手×骨架矩阵、第 193 章的装备联合裁决，全部建立在这个端点上。

用一组真实数字体会差距。09-21 快照里，「孙悟空完全体」（孙悟空+阿轲+露娜+周瑜四件套）的条件登顶率是 39.39%（25,914 局），而孙悟空的边际登顶率只有 25.10%。同一个英雄，两个口径差了 14 个百分点——差的就是「队友有没有把体系凑齐」这一层。边际统计告诉你孙悟空值得抢（25.10% 仍远超 16.7% 基线），条件统计告诉你什么时候值得 all-in（四件套凑齐是另一个游戏）。**读榜定热度，条件定打法**——这两个动作要用两套工具，混用是新手管道最常见的浪费。

但工具越锋利，越要先讲清楚它不能干什么，这里先把最大的那把刀立起来：**条件统计仍然不是因果。**「含三核骨架的对局登顶 46.6%」不能推出「你玩三核就有 46.6%」——能凑齐三核的局本身就经过了层层筛选（经济没崩、没被抢牌、玩家水平），这是幸存者偏差，第 197 章红队攻击一号。条件查询给你的是**条件化的事实**，从事实到「你该怎么做」之间，还隔着对照设计（本章第五节）和 10 局实测（第 194 章）。

## 二、explore 端点参数手册

端点：`POST https://api.datatft.com/wzwxq/explore`。请求体逐字段拆解——这份手册的每个字段都实测验证过，不是猜的：

| 字段 | 类型 | 填什么 | 错了会怎样 |
|---|---|---|---|
| `time` | 数字 | `7`（7 天窗口，与榜单同口径） | 填别的值口径就与快照对不上 |
| `operator` | 字符串 | `"AND"`（多条件同时满足） | 改语义前先想清楚你要什么 |
| `advancedMode` | 布尔 | `false`（实测场景没用到 true） | 未知开关，保守关着 |
| `filters` | 数组 | 条件数组，见下 | 空数组=无条件，返回全局池 |
| `exclusions` | 数组 | 排除条件，结构与 filters 相同 | 用于「含 A 但不含 B」 |
| `page` / `pageSize` | 数字 | `pageSize: 12`，page 从 1 起 | 深页大量重复（第六节） |
| `version` | 字符串 | `"v1"` | 与其他端点保持一致 |

filter 的结构是四个字段的固定组合：`{"type": "hero", "id": "5031", "switchVal": true, "conditionVal": true}`。`type` 是条件维度——实测确认的有 `hero`（英雄在场）、`commander`（棋手）、装备维度（`eq-combo-query` 用同一结构传装备 id）；`id` 是**字符串化的数字 id**（英雄/棋手/装备各自的 id 体系，必须从本地卡牌库翻译，映射不到就放弃这条查询，绝不禁用猜测 id——猜错一个 id，你统计的是一个不存在的阵容）；`switchVal` 与 `conditionVal` 官网 UI 恒为 true，实测保持 true 即可——这两个字段的真实语义没有逆向出来（可能是开关与条件的 UI 状态位），手册里照实标注「未知、恒 true」，这是手册的一部分：**写明你不知道的，和写明你知道的同样重要**。**多个 filter 用 AND 串起来就是「对局里同时含这些英雄」**——`['露娜','孙悟空','太乙真人']` 三个 filter 查的就是三核骨架的 6,386 局。

响应体的 `data` 有两组东西，第六节专讲口径差别；先记字段清单：`base`（条件池的聚合统计：`count` 样本局数、`firstRate`、`top3Rate`、`avgPlacement`）、`total`（橱窗可取回的明细条数上限）、`heroes`（条件池内英雄榜）、`equipmentRecommendations` / `threeItemBuilds`（条件池内的出装推荐）、`counters`（对位数据）、`matches`（翻页取回的逐局明细）。**`base` 是统计的主产出，其余全是条件池内的二级切片**——比如查三核骨架时，`heroes` 告诉你在这些局里加第四个英雄谁的表现最好，第 194 章的四核梯度就是从这类切片里读出来的。

## 三、参数从哪来：一次接口逆向的完整过程

这套参数结构不是文档给的——datawxq 没有开放 API 文档，explore 是官网「探索者」页面的私有接口。拿到它的完整过程值得复述一遍，因为**下次接口改版，你唯一的复原手段就是重做这件事**。

工具是 `explorer-recon.mjs`（浏览器勘察脚本，playwright-core 驱动系统 Chrome），四步：

1. **挂监听**：`page.on('request')` 抓所有 URL 含 `/explore` 的请求，把 postData 存到 `/tmp/explore_reqN.json`；`page.on('response')` 抓响应体存 `/tmp/explore_resN.json`，顺手打印 `data` 的键名清单。
2. **驱动界面**：打开 `datawxq.com/explorer`，等网络空闲，然后像真人一样操作——点击「太乙真人」「瑶」两张英雄卡，再点「添加排除条件」选一个英雄。
3. **对照提取**：每点一次，界面就发一次 explore 请求。对比点击前后的请求体，多出来的数组就是刚才那个动作的序列化结果——点英雄卡多出了 `filters` 里的一项，加排除多出了 `exclusions` 里的一项。
4. **固化验证**：把逆向出的请求体拿去直连重放，响应与页面一致，参数手册才算建立。

这个过程的原则是「**让界面替你写文档**」：你在 UI 上的每个操作都被编译成一个请求体，逆向就是反编译这个编译过程。它同时给了一个副产品——**知道界面上有哪个开关，就知道请求体里可能有哪个字段**。`advancedMode` 就是这么发现的：界面上有个「高级模式」开关，虽然实测场景没用到，但它的存在被记录在手册里，留待将来。

有人会问：为什么不直接猜参数？REST 风格的接口就那几样东西，`filters`、`exclusions`、`operator` 听名字都能编出来。答案是第六节的 `lineups/search` 案例：**猜错的参数不会报错，会安静地返回一份错误口径的数据**。猜 `heroId` 直接放顶层字段，服务端不认，返回全量榜——你以为在查「含钟馗的阵容」，实际拿到的是无过滤的热门榜，后续所有分析都在错误的切片上进行，而且毫无异常报错。逆向慢，但逆向出来的每个字段都带「界面动作 → 请求变化 → 响应变化」的完整证据链；猜参数快，但省下的半小时会在三天后用十倍的时偿还原。

顺带说清时间线：09-14 上线当天，项目记录里写的是「explorer 查询接口待逆向」——当天只摸清了六个榜单端点。explore 是后来补上的，用的就是上面的流程。所以「待逆向」不是永久状态，是一份待办的工单；这份工单的解法，比工单本身更值得记进书里。

## 四、filters 的组合语义：AND、排除与对照设计

参数手册是语法，组合语义才是语义学。三种最常用的组合模式，各配一个 09-21 快照的实测结果：

**模式一：多英雄 AND（阵容条件）。** `['公孙离','猪八戒','张良','鬼谷子','云中君']` 五个 filter 查「公孙离融合」：`base` 返回 3,977 局、登顶 38.27%、前三 82.65%、均次 2.23。同一份脚本里的「公孙离标准」（公孙离+虞姬+鬼谷子+少司缘+张良）是 37,046 局、登顶 32.62%。**两条对照着读才有意义**：融合变体更強（+5.65pp）但样本只有标准的九分之一——这正是对照设计的价值，单查任何一条，你都可能把「小样本的运气」或「大样本的平庸」当成结论。

**模式二：加排除（刻画「不含」）。** `exclusions` 与 `filters` 结构相同。最有用的场景是**拆解贡献**：查「露娜+孙悟空」（双核）与查「露娜+孙悟空+太乙真人」（三核）做差，差出来的就是太乙真人的边际贡献——34.60% 到 46.62%，**+12.0pp 登顶、+18.5pp 前三**，这一个数字确立了太乙真人「必要件」的地位（第 194 章专讲）。排除条件还可以做反向刻画：「含三核但不含钟馗」——确认钟馗加进来之前的天花板在哪里。

**模式三：英雄×装备联合（出装裁决）。** filter 里同时给英雄和装备各一条，「露娜局中带着魔律之刃」的登顶率与「露娜局」整体做对照。这是 `eq-combo-query.mjs` 的领地，证据等级高于 fit 矩阵（第 193 章的裁决流程），因为联合条件至少把「带这件装备的人」钉死在了「玩这个英雄的人」里面。

**模式四：棋手条件（先验校准）。** filter 只给一条 `commander`，查「这个棋手的对局池」。它有两种用法。显性用法是第 194 章的全矩阵——棋手单查配棋手×骨架联合查，差集就是绑定强度。隐性用法更日常：**给第 171 章的对手卡喂先验**。09-21 的实测：三核骨架的全部 2,977 局橱窗明细里，孙小宾与镜两家合计 1,738 局，占 58%——「看到孙小宾坐进对局，就上调他走三核线的先验」这条局内直觉，背后就是一次棋手条件查询。对手建模的原料在局内，但先验的校准在赛前，这个端点是把两者接起来的那根线。

响应体里还有两块二级切片值得点名。`heroes` 是条件池内的英雄榜——查三核骨架时，它列出这些局里其余英雄的表现，第四个核心（钟馗还是海月）的选择就靠它缩小候选；`counters` 给对位信息，骨架对热门体系的相性可以从这里预读。纪律与主线相同：切片数字同样吃样本量，`count` 小的切片只当线索。

组合的两条纪律。**其一，每加一个条件，样本按乘法蒸发。** 三核 6,386 局，加钟馗剩 743 局，再加海月剩 150 局——条件从三个到五个，样本从六千掉到一百五。150 局的登顶率（70.67%）方向上可信（五核确实是最强形态），绝对值已经进入噪声区。设计查询前先估样本预算：**主线结论的样本底线建议 1,000 局，方向性结论 300 局，再往下只配当线索。** 其二，对照查询必须控制变量。比较两组条件时，除目标差异外其余维度尽量对齐——样本量差一个量级的对照，读的时候要自动降一档置信度。

## 五、三个口径：base、total 与橱窗明细

explore 响应里最容易被混用的就是这三个东西，09-21 快照的全局查询（无条件、空 filters）把它们的数量关系摆得很清楚：`base.count` = **1,137,509**（聚合统计的真实样本，7 天全部对局），`total` = **189,629**（服务端报告的橱窗可取回明细条数）。也就是说，**你翻页能摸到的明细最多只占聚合样本的六分之一**，而且深分页重复严重——09-21 的对抗性审查实测：橱窗抓 240 条，按 `gameTime + 阵容签名`（英雄 id 排序元组）去重后只剩 **114 局唯一对局**，重复率过半。

口径纪律由此而来，一句话：**统计看 `base`，样本用明细。**「三核 46.62%」这种要写进结论的数字，必须出自 `base`——它基于 6,386 局的完整聚合，没有重复计数问题。明细（`matches` 翻页）的价值在另一个维度：它是唯一带**逐局细节**的口径——每局的棋手、天赋、站位单位的等级/装备/伤害、总等级、最终回合。「高强度局里主流体系长什么样」只有明细能回答：`explore-sample.mjs` 按 12 条/页采 30 页，`hs-analysis.py` 去重后按总等级分强度档（high=1200 ≈P75、top=1600 ≈P90），再做 Jaccard≥0.6 的阵容原型聚类。聚类的产出形态是「原型卡」：每个原型记样本数、登顶率、前三率、均次和出现最多的七个英雄——比如超顶级橱窗里的「镜绝活」原型（孙悟空+露娜+阿轲+周瑜+甄姬+小乔）在聚合口径下有 22,871 局、登顶 40.19%，这种「明细里看结构、聚合里验强度」的两段式读法，是这两个口径配合的标准姿势。**单独任何一段都会骗人**：明细无聚合则样本可疑，聚合无明细则不知体系内部长什么样。**两条路都要走，但把各自的数字标上各自的口径**——「去重后 114 局」和「聚合 6,386 局」差着五十七倍，混写一个 n 就是自欺。

## 六、lineups/search 的过滤参数：一次失败的逆向与它的替代方案

参数手册里有一个负面案例值得单独立传：热门阵容接口 `lineups/search` 支持按英雄 id 过滤——至少文档意义上如此。实测的结果是：**过滤参数提交了，服务端不认，返回的仍然是无条件的热门榜**。这类「参数在、行为不在」的接口比纯无参数的更危险，因为它会安静地给你一份错误口径的数据：你以为查的是「含钟馗的阵容榜」，拿到手的是全量榜。

处置方案是**全量拉取 + 本地过滤**：把阵容榜整页取回（每条阵容带 `recommendedUnits` 的英雄名与出场率），在自己的代码里做「包含某英雄」的筛选。代价是传输量大一点，收益是三个：过滤逻辑在自己手里、永远正确；想改条件不用重新请求（查询成本降一个量级）；还能顺手做服务端给不了的分析——比如按「太乙真人在阵容里的出场率」给热门阵容分层（09-21 榜单里太乙在多条主流阵容中的出场率 22%~87% 不等，这层结构只有本地过滤后才看得见）。

这条案例的一般化教训写进可迁移原则：**接口的每个参数都要有一次「正反对照」验证才允许进手册**——查一次带条件的、查一次不带条件的，两者结果不同，参数才算生效。文档、字段名、参数名都不能作为「已生效」的证据。

## 七、常见错误

1. **条件堆太多，样本蒸发后还在读数。** 五条件查询跑出 150 局 70.7% 的高分就当结论用——150 局的 95% 置信区间宽到能开进一支车队。先查 `base.count`，低于 300 只当线索。
2. **拿橱窗明细算统计。** 明细有深分页重复（240 条 → 114 局），拿来算登顶率等于给小样本再乘一个虚假的权重。明细只做结构分析，统计一律回 `base`。
3. **id 靠猜。** 英雄、棋手、装备三套 id 体系互不通用，本地库映射不到的名字就跳过——一个错 id 会安静地统计出「0 局」，或者更糟，匹配到别的对象。
4. **对照查询不控变量。** 「三核+钟馗 743 局」对「三核+海月 828 局」可以直接比；但「孙小宾绝活 19 局」对「镜绝活 22,871 局」的差距里，样本量本身就是最大的变量（第 194 章为 19 局那条线单独设了观察条款）。
5. **忽视礼貌约束。** 查询间不 `sleep 1.5s`、42000 之后还连发——第 191 章已经记过账：这个源对高频请求的真实惩罚是 IP 级封禁，封的是你未来一周的所有数据。查询脚本里的 `blocked` 标志位一旦置位当日就不再发请求，这是故意的。
6. **把条件登顶率当承诺。** 「公孙离融合 38.27%」描述的是**已经打出来的局**的平均结果，不是你打 fusion 会有的结果。执行差距、样本筛选、环境变化三重折扣之后，才是你的期望值——精确的折扣率只能用 10 局实测标定（第 194 章协议）。
7. **查询不做存档。** 请求体只留在终端历史里，三天后想复核「这个数字当时是怎么查出来的」就无从对账。查询体与响应都要落盘进当日快照目录——分析层的产出和采集层的数据适用同一条纪律：不能回溯的数字不配进结论。

## 八、落到执行：本章的决策出口

**查询设计清单（每个新问题过一遍）：**
1. 把问题翻译成条件：主条件是什么、对照条件是什么、要不要排除项？
2. 样本预算：主结论 ≥1,000 局、方向结论 ≥300 局，先估后查；不够就放宽条件，而不是硬读小样本。
3. id 全部走本地卡牌库翻译，映射失败即放弃该条。
4. 查询体存档进当日 `data/meta/<日期>/`，响应原样落盘——三个月后红队复核时，请求体和响应体都是证据。

**三条硬规则：** 查询间 sleep 1.5s；42000 当日停机；每个写进结论的数字必须能说出「来自哪次查询、哪个字段、样本多少」。

> **本章可迁移原则：**
> 1. **没有文档的接口，界面就是文档。** 每个按钮都是一个请求编译器，点击操作就是在生成规格说明——逆向的本质是反编译人机交互。
> 2. **统计口径与明细口径必须分账。** 聚合数字回答「平均多少」，明细样本回答「长什么样」；两边数字混写一个样本量，是数据分析里最隐蔽的自欺。
> 3. **条件统计逼近的是「筛选后的平均」，不是「你的未来」。** 条件设计得越像你真实要执行的决策，参考价值越高；但最后一道折扣（你 vs 平均玩家）只有实测能标定。
