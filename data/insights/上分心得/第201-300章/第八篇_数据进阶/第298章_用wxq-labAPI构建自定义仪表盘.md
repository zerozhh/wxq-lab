# 第二百九十八章 · 用 wxq-lab API 构建自定义仪表盘

> **读完这章你能**：把散落在 data/ 目录里的几十个 JSON 和五六个采集脚本，组装成一个每天 30 秒扫完的个人仪表盘——懂三层架构（快照数据层 / 查询管道层 / 展示层）各管什么、知道本机 IP 已被封的前提下哪些接口还能直连、会写一个聚合脚本和一页 HTML，并且让仪表盘在数据冻结期诚实地标出自己有多旧。

---

## 一、原理：仪表盘不是图表集合，是一道决策压缩题

先纠正一个方向性误解：仪表盘的目的不是「把数据画出来」，是**把你每天要做的三个判断从翻十遍目录压成扫一眼**。这三个判断对本项目是固定的：今天练什么（哪个体系值得投入周期）、环境变了吗（昨天到今天有没有跳变、我的体系还活着吗）、我打得怎么样（个人模型的本周期读数对不对得上先验）。凡是回答不了这三个判断里任何一个的面板，都是装饰——判断覆盖率是仪表盘的第一设计约束，先有问题，后有面板，顺序不能反。

第二个约束是时间预算：仪表盘的形态要服务「30 秒扫完」。这决定了信息密度的排布逻辑——**最重要的读数放最大的字号，放在固定位置**。每次打开页面，视线路径应该完全一致：先看顶栏的管道状态徽章（数据能不能信），再看三个 KPI（本周期登顶率对判定线、最近环境变动、我的体系是否还在主流池），最后才下钻到细节面板。对比一下失败形态：一个信息均匀铺开的页面，每次看都要重新决定「从哪看起」，30 秒变成 3 分钟，一周后你就会放弃它回到「直接翻 summary.md」。扫读路径的一致性不是审美偏好，是工具能不能活过三周的生死线；第二百九十五章的「三行结论」之所以规定成格式，是同一个道理——固定格式压缩读取成本，读取成本决定工具会不会被持续使用。

技术形态是三层架构，每层的职责边界要划死。**数据层**：`data/` 下的 JSON 是唯一事实源——`data/meta/<日期>/api/` 存每日原始快照（heroes、commanders、equipment、lineups、equipment-fit、trend-hero 六件套），`summary.md` 是当日环境摘要，`comp-stats.json` 是条件查询的产物，`updates.log` 是采集管道的运行日志。数据层只有一条铁律：**先有快照，再有一切**——任何展示、分析、结论都从快照读，不从「我记得昨天看到什么」读。**管道层**：脚本负责把原始快照变成可读的中间产物——`fetch-meta.mjs` 拉每日六件套，`update-service.mjs` 在每天 08:53 定时驱动它，`comp-query.mjs` 与 `cmd-comp-query.mjs` 走 explore 接口做阵容与棋手×骨架的联合条件查询，`eq-combo-query.mjs` 做英雄×装备联合查询，`meta-evolution.py` 跨日对比出趋势。管道层的纪律是**幂等与可重跑**：任何一脚本挂了，重跑一次必须得到同样的结果，不产生半成品状态。**展示层**：前端只做两件事——读中间产物、渲染；不做任何计算。计算在前端发生的仪表盘，每换一台机器就多一份口径漂移的可能。

本项目有三条现实约束，直接决定了架构形态，别处的教程不一定会遇到。**约束一：第三方 API 没有 CORS 头**，浏览器直连 `api.datatft.com` 一律被拦，所以前端永远走 `serve.mjs` 的 `/api/datatft/*` 代理转发——这是硬规则，没有例外。**约束二：本机 IP 已被源站封禁**（09-16 起 fetch 返回 `code=42000` 且错误信息里带本机出口 IP），本地直连采集已死，采集必须走 GitHub Actions 的出口——这意味着你的仪表盘要假设「数据是异地定时推过来的」，本地脚本只剩读和聚合的职责。**约束三：数据源 09-20 起整体冻结**——聚合、榜单、趋势、橱窗全部停更，只有 lineups 和 equipment-fit 还活动。三条约束合起来是同一个结论：**仪表盘必须活在「离线快照为主、活动接口为辅」的混合模式**，并且每一块面板都要知道自己读的数据有多旧——冻结感知不是高级特性，是这个项目的仪表盘能不能信的基本盘。

## 二、数据支撑：盘点你手里有什么、长什么样

每日快照六件套的字段形状，聚合脚本要按这个写。榜单类（heroes/commanders/equipment）每条记录含样本数、登顶率、前三率、平均名次（英雄榜多一个平均等级）；装备 fit 是 85 英雄 × 72 装备的登顶率提升矩阵（winRateLift，约六十万场样本）；trend-hero 是英雄的跨日趋势序列；lineups 与 equipment-fit 是冻结后仍在活动的两个端点。条件查询产物的形状以 comp-stats.json 为准：`global.base` 给全局基线（1137509 场、登顶 16.7%、前三 50.0%、均次 3.50），每个阵容条目含英雄清单、条件统计（样本数、登顶、前三、均次）、池内总量和 topHeroes 明细——**阵容的「存在率」要自己算**：该阵容样本数除以全局基底，09-22 口径下李信运营 5.19%、孙悟空完全体 2.28%，这两个数字榜单不直接给，仪表盘的聚合层必须补上。

聚合层最有价值的三类派生指标，全部能从现有快照算出。**第一类：基线相对差**——任何条件值减去 16.7% 基线的差值比绝对值可读（「40.2% 登顶」不如「比基线高 23.5 个点」直观，且相对差天然免疫样本量漂移的一部分干扰；第一百九十三章讲 fit 矩阵时立的规矩「绝对值仅供叙事、排序才可信」在这里同样生效）。**第二类：日环比结构变化**——updates.log 里每条成功记录自带 `summary`（heroesUp/heroesDown/heroesEntered/heroesLeft/lineupsEntered/lineupsLeft），连续几天的 summary 拼起来就是环境的变动率曲线；09-16 那条 `heroesLeft: 85` 的假信号（全部下架，实为封禁前兆）说明这个字段不只描述环境，还是管道健康的哨兵——** entered/left 的异常值首先指向数据源故障，其次才是环境变化**。**第三类：个人面板**——`data/matches/` 的复盘记录聚合成本周期登顶率、均次、名次分布，与 meta 面板并排；仪表盘把「环境」和「我」放在同一屏，是第二百九十五章滚动对照的日常化形态。

个人面板的聚合粒度直接沿用第二百九十五章定义的周期结构，不需要新造口径。输入是 `data/matches/` 下的复盘 JSON：每局一条，含名次、棋手、最终阵容、关键天赋、装备分配、决策点、对手阵容。聚合输出四组读数：其一，本周期（最近 10 有效局，练习局剔除）的登顶率、前三率、均次，各带样本量；其二，名次分布直方图——1 到 8 名各几局，5、6 名堆积还是 1、8 两极分化一眼可辨（分布形状是止损缺陷的诊断书，比均次多还原一层过程）；其三，分棋手切片——你在不同棋手上的实测差，就是第二百九十五章说的「执行系数按棋手分解」；其四，实验标识读数——装备分配字段里 A/B 标注的分组计数，确认当前实验两组各攒了几局、还差几局到评估点。这四组读数让仪表盘成为验证周期的日常仪表：不用等周期结束开电脑算，每天打开就看到「实验进度 7/10、本周期暂 2 登顶、名次分布向 5、6 名堆积」。

冻结的判别信号也来自数据本身，写进聚合脚本当哨兵。三个信号：其一，**跨日快照哈希**——09-20 与 09-22 的 summary.md 逐字节一致、装备榜样本恒定在 1137509 场，样本量纹丝不动就是冻结的实锤；解冻的实锤同样是它：样本量重新开始增长。其二，**文件时间戳**——`api/` 目录六件套的 mtime 若连续多日不更新而 updates.log 仍报 ok，说明抓到的是缓存或降级响应。其三，**code 字段**——正常响应无 code 或 code 为成功值，`code=42000` 是风控封禁的签名（错误串里带出口 IP），别把它和「数据没更新」混为一谈：42000 是管道问题，冻结是源站问题，处理路径完全不同（前者换出口，后者等解冻并转个人数据）。仪表盘的状态徽章就应该由这三个信号驱动：绿色（快照当日新鲜）、黄色（快照陈旧但管道正常）、红色（管道故障）、灰色（源站冻结）——四态是最低配置。

活动中的两个端点（lineups、equipment-fit）在冻结期反而是最需要警惕的面板，原因是一条容易搞反的因果：**接口活动 ≠ 数据活跃**。lineups/search 和 equipment-fit 的接口确实还在返回响应，但它们统计的对局样本仍在被源站以某种口径聚合——解冻前的窗口结构没人能验证，这两个面板的数字可能与冻结前的榜单出现系统性错位（窗口不同、筛选不同、更新节奏不同）。所以聚合脚本对这两块的处理是：照常抓、照常存快照序列、但面板上加「独立口径」标记，它们的读数只做趋势方向参考，不与冻结前的榜单数字直接拼接比较——「接口活着」的面板如果不打标记，就是仪表盘里最会骗人的那块。

## 三、实操：从零到一页仪表盘的五个步骤

第一步，写下你的三个问题，砍掉答不了的面板。示例配置：问题一「今天练什么」由三块面板回答——体系强度条（comp-stats 的存在率 × 条件登顶率，按相对差排序）、装备 fit 头部（我常用英雄的前 10 装备，按 winRateLift 排序，标注冻结口径日期）、棋手榜变动；问题二「环境变了吗」由两块回答——updates.log 的 summary 折线（up/down/entered/left 四条）、跨日榜单对比（meta-evolution.py 的输出）；问题三「我打得怎么样」由复盘聚合面板回答——本周期登顶率对 30% 判定线、均次对 2.9、名次分布直方图。九块面板，多了就砍：**面板数量的上限是「每块都能说出回答哪个问题」**，说不出来的那个现在就删。这一步看似虚，实际是整个工程里回报率最高的一步——后四步的全部技术选择（聚合粒度、版式、自动化的优先级）都由这三个问题派生；跳过它的直接后果就是错误一里那座三周后没人看的陈列馆。顺带划清与第一百九十一、一百九十二章的分工：那两章讲的是「管道怎么建、查询怎么写」，本章讲的是「建成之后怎么把读数组织成每天要用的驾驶舱」——管道是仓库，仪表盘是驾驶舱，前者重准确，后者重压缩，两边的失败模式完全不同。

第二步，写聚合脚本。一个 Node 脚本，输入是 `data/meta/` 目录和 `data/matches/`，输出是单文件 `dashboard.json`，骨架大致是：

```js
// scripts/build-dashboard.mjs
import { readdir, readFile, writeFile } from 'node:fs/promises';

const days = (await readdir('data/meta')).sort().slice(-14);      // 最近 14 天
const api  = {};                                                   // 日期 → 六件套
for (const d of days) {
  try {
    api[d] = {
      heroes: JSON.parse(await readFile(`data/meta/${d}/api/heroes.json`, 'utf8')),
      fit:    JSON.parse(await readFile(`data/meta/${d}/api/equipment-fit.json`, 'utf8')),
    };
  } catch { /* 缺日跳过，绝不崩进程 */ }
}
const log  = (await readFile('data/meta/updates.log', 'utf8'))
  .trim().split('\n').map(JSON.parse);
const comp = JSON.parse(await readFile('data/meta/2026-09-22/comp-stats.json', 'utf8'));

const base = comp.global.base;                                     // 1137509 / 16.7%
const out = {
  generatedAt: new Date().toISOString(),
  freshness:  { lastGoodDay: days.at(-1), frozen: /* 跨日哈希对比 */ true },
  baseline:   { first: base.firstRate, avg: base.avgPlacement, n: base.count },
  comps:      Object.entries(comp.comps).map(([k, v]) => ({
                name: k, presence: v.base.count / base.count,
                lift: v.base.firstRate - base.firstRate, avg: v.base.avgPlacement })),
  updates:    log.slice(-30).map(e => ({ date: e.date, ok: e.ok,
                up: e.summary?.heroesUp, left: e.summary?.heroesLeft })),
};
await writeFile('dashboard.json', JSON.stringify(out));
```

要点三条：**容错优先**（缺日、缺字段一律跳过，聚合脚本崩一次，仪表盘就空一次）；**派生指标在聚合层算完**（presence、lift、freeze 判定都不留给前端）；**输出单文件**——展示层只读这一个文件，缓存、调试、迁移都简单。

第三步，做展示页。最小方案：一页静态 HTML 加内联 CSS/JS，读 dashboard.json 渲染，`serve.mjs` 直接供静态文件（它本来就在 :5177 供 dist 和 data）；需要活动数据的两块（lineups、equipment-fit）单独走 `/api/datatft/*` 代理——**冻结面板读本地、活动面板走代理**，两种来源在视觉上用同一个新鲜度徽章区分。进阶方案：在 ui/ 里加一个视图（views 目录下已有 MetaView、TierView、EquipmentFitView、ExplorerView、WorkshopView、CoachView、CodexView、HeroDetailView、FactionsView、LogView 十个视图，新视图照抄现有路由与单根节点约定），复用 Tailwind 主题 token。版式给一个可直接抄的骨架：顶栏一行四件套——管道状态徽章（绿黄红灰）、最后成功采集日期、冻结标记、生成时间，这一行是仪表盘的「数据可信度声明」；主区三列（窄屏自动叠放为单列），左列环境（体系强度条、榜单变动），中列个人（周期读数、名次分布、实验进度），右列工具（条件查询快捷入口、fit 头部）。体系强度条用「连通数据条」形态——名字、存在率、条件登顶率、相对基线差排在同一条横带上，而不是九张同质卡片，这是本项目前端已确立的设计语言，照抄即可。图表只出现在两处（summary 折线、名次分布直方图），其余全是数字与排序——**图表是奢侈品，每多一张就多 5 秒读取成本**。无论哪种方案，展示层的硬规矩：图表系列色只用已过浅底 CVD 验证的两支（蓝 #4a79ff、橙 #d95926），样本量低于 1000 的行直接不渲染或置灰（样本门槛是展示层纪律，不是数据层纪律——数据层存全量，展示层守门槛）；表格默认按相对差排序而非绝对值；中文不挂斜体类。

第四步，接自动化。采集端：本机 08:53 的 cron 继续保留（走 GitHub Actions 出口时本地只做触发与落盘），Actions 的工作流每日定时拉数、提交回仓库——**仓库即数据库**，任何一台机器 clone 下来就有全部历史。告警端：update-service 已经把失败（含 42000 全文）追加进 updates.log，聚合脚本顺手产出管道状态（最近 3 日 ok 数、最后成功日期），仪表盘顶部常驻四态徽章；徽章变红超过一天就处理，管道的沉默失败是最贵的失败——它不报错，只是让你的所有面板慢慢变成旧报纸而不自知。

自动化的拓扑要按「封禁现实」设计，这是本项目与其他教程差异最大的一处。正常世界的架构是「本机定时 → 直连 API → 落盘」三段；本项目的现实是中间那段在本机已死（42000 封禁），所以架构改成「本机定时 → 触发 GitHub Actions → Actions 的出口拉数 → 提交回仓库 → 本机 pull 落盘」。改动只有一个环节（拉数的执行位置），数据层的契约完全不变——这正是三层架构的回报：换出口不动契约。落地时三个细节：Actions 的定时用 UTC 表达（北京时间 08:53 是 UTC 00:53，别差一小时）；工作流里的失败必须显式失败（exit 非 0），静默成功比失败更糟——updates.log 的错误条目就是靠失败退出码触发的；仓库提交信息里带日期与 ok 状态，让 git log 本身成为第二份运行日志。若某天 Actions 出口也被封，架构再降一级：手动浏览器模式（WXQ_FULL=1 的全量抓取，截获页面全部 JSON 手动入库）——丑，但契约依旧不变，仪表盘照常工作。

第五步，冻结期的特殊守则。冻结不等于停工：lineups 和 equipment-fit 还活动，这两块的每日快照继续拉、继续入快照序列（解冻后它们是衔接新旧环境的唯一连续段）；冻结面板的日期徽章放大加粗——**用户（就是你自己）必须在任何时刻知道这块面板的数据是 09-20 口径还是今天口径**；条件查询类面板（comp-stats）在冻结期标注「结构先验，按第二百九十六章规则降级使用」。解冻那天的动作清单不在本章展开（第三百章是它的家），但仪表盘要预留入口：freshness 字段一旦从 frozen 翻回 false，页面顶部给一条通栏提示——解冻首周是结论最混乱的窗口，仪表盘有义务在你扫一眼的时候提醒这件事。

## 四、常见错误：五种翻车与纠正

**错误一：堆「能算的」而不是「要用的」。**把能拿到的每个指标都画成图，二十块面板蔚为壮观，三周后你自己都不看了。仪表盘的死法大多是这个：它变成了数据的陈列馆而不是决策的驾驶舱。纠正：判断覆盖率审查——每块面板回答哪个问题、触发什么行动，答不出来的面板删除；每月重审一次，你的三个问题变了，面板跟着换血。补救：已经堆起来的，按过去 30 天「看过且用它的结论做过决定」的次数排序，尾部一半直接砍。

**错误二：跨冻结边界画连续曲线。**把 09-14 到今天的每日快照连成一条趋势线，中间夹着 09-16 的封禁断点和 09-20 的冻结断点——这条线的斜率、波动、拐点全是伪影，读出来的「趋势」没有一条可信。纠正：断点纪律（第二百九十二章）在前端同样执行——断点两侧分段渲染，断点处画虚线并标注事件（「采集切换 Actions 出口」「源站冻结」）；冻结段的数据点用空心标记。补救：已经画了连续线的，先在断点处切开再谈任何解读；切完之后多半会发现冻结段根本不构成曲线，只剩两个点——那就如实显示两个点。

**错误三：前端直连第三方 API。**图省事在页面里直接 fetch `api.datatft.com`——CORS 拦截是第一层死，本机 IP 封禁是第二层死，就算都绕过去，源站一冻结页面就白屏，而你分不清是冻结还是代码坏了。纠正：浏览器永远只跟自己的后端说话（serve.mjs 代理或本地静态数据），代理只给活动端点用；这条规矩在第一百九十一章的管道设计里就立过，本章只是强调它在封禁 + 冻结双重现实下从「规范」升级成了「物理」。

**错误四：绝对值迷信。**面板大字渲染「登顶率 40.2%」「winRateLift +27pp」，读者（你）默认它们是无条件增益——但 40.2% 是凑齐阵容后的条件值，+27pp 继承着「能做成装的局本来就更接近赢」的幸存者偏差（第二百九十一章红队的原话）。纠正：条件值面板一律带基线参照（16.7%）或相对差刻度；fit 类数字的标题写「相对排序依据」，正文写「绝对值仅供叙事」；样本量门槛之下不渲染。补救：已经造成的误读不用回溯修复，把口径注释补上，从下一眼起按新口径读——仪表盘的好处是纠正成本只有一行字。

**错误五：无告警的静默失败。**采集挂了三天没人发现，仪表盘每天照常渲染——渲染的是三份一模一样的旧数据，你基于它做出的「环境很稳定」的判断完全是管道故障的倒影。纠正：四态徽章 + updates.log 检查进聚合脚本（本部分第三步的现成结构）；summary 里 heroesUp 和 heroesDown 连续多日全为零，即使 ok=true 也算疑似异常（可能是解析失灵——源站改了字段而脚本没跟上，抓回来的是空壳）。补救：发现静默失败后，先核实最后一份真实新鲜数据的日期，该日期之后的所有分析结论标注「基于陈旧数据」，该撤的重读。

## 五、可迁移原则

1. **仪表盘是决策压缩，不是数据陈列。**先写下你要做的三个判断，再让每块面板认领一个——认领不了的面板是装饰，装饰会稀释你扫一眼时找到关键信息的概率。
2. **三层各管各的：数据层存事实，管道层算派生，展示层只渲染。**计算漏进前端的那一刻，口径漂移就开始了；聚合脚本输出的单文件 JSON 是层与层之间唯一的合同。
3. **新鲜度是仪表盘的一部分。**四态徽章、口径日期、断点虚线——用户必须在任何时刻知道每块数据有多旧；冻结与封禁不是异常状态，是本项目仪表盘的常态设计输入。
4. **浏览器不直连第三方。**CORS、IP 封禁、源站冻结三重现实下，代理与本地快照是唯一稳定的读取路径；把「哪里来的数据」标进每个面板的角落。
5. **管道的沉默失败是最贵的失败。**ok=true 不等于健康——样本量恒定、变动率全零、跨日哈希一致，这些「太安静」的信号要当成告警处理；仪表盘的第一块面板永远是管道自己的状态。
