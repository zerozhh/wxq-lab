# 第三百章 · 上分心得的未来：数据源解冻后的更新指南

> **读完这章你能**：在数据源解冻的那一天（它一定会来），按正确的顺序把系统拉起来——先验管道再碰结论、等窗口翻新再下判断、按保鲜度给三百章结论逐项办续期或办注销，并且让整个架构保持「随时能再冻一次」的姿态，因为这次解冻不是终点，是冻结周期的间隙。

---

## 一、原理：数据会过期，但过期速度分三层

解冻指南的全部逻辑，建立在一条容易被忽略的区分上：**数据有保质期，但不同结论的保质期差着量级**。把全书的资产按保鲜度分三层，解冻日该做什么就一目了然。**机制层**：卡牌库（85 英雄的面板、技能、觉醒，21 棋手的技能与秘技，73 装备的合成树与效果，255 天赋牌）——它们的失效条件是版本更新而不是数据冻结；只要没打补丁，`data/heroes.json` 这套库存永远是准的，冻结一年也不需要动。**统计层**：榜单、装备 fit、阵容排行、趋势——冻结即过期，且**解冻不等于恢复**：源站恢复推送的那一刻，新数据从零开始累积，time=7 的窗口要整整七天才翻新成纯粹的新世界；统计层的结论在解冻日全部自动降级为「待重验」，没有例外。**方法层**：贝叶斯推断的流程、A/B 的设计纪律、去卷积的思路、对抗性审查的清单、样本量纪律——方法不依附于任何一批数字，永不过期；过期的只是喂给方法的旧数字。

这条分层直接推出解冻日的第一反应：**先验管道，再碰结论**。解冻的诱惑是立刻抓数、立刻更新所有面板、立刻宣布「环境回来了」——正确的动作序列完全相反：先确认管道健康（探测、比对 schema、核对样本量守恒），再让新数据安静地积累，最后才轮到结论层的换血。顺序错了的代价不是浪费一天，是把「半新半旧的混合窗口」当成新环境来读，产出整整一周的假结论——冻结期你至少知道自己拿的是旧数据，混合窗口最危险的地方是它看起来很新。第二百九十二章的断点纪律在这里全面生效：**解冻是一个断点，断点两侧的数据不可混算**，旧窗口的使命到此为止，新窗口的结论从第一个纯新数据日开始。

第三条原理是本系列一以贯之的压舱石：**个人数据线永不冻结**。`data/matches/` 里的复盘记录、你的执行系数、你的名次分布、你的 A/B 实验卡——这条线只依赖你自己打的游戏，源站冻不冻结与它无关。解冻指南因此不是「恢复依赖」的指南，是「衔接两条线」的指南：冻结期的三四周里，你的个人模型是唯一活着的先验源（第二百九十六章的个人出现率表、第二百九十五章的滚动对照都在靠它）；解冻后，公开数据线复活，它的工作不是取代个人线，是给个人线重新提供**环境先验**——个人线继续负责回答「在我手里怎么样」，公开线重新接手「环境里什么可行」。两条线的分工从第一天起就写死了，解冻只是把缺了三周的那条补回来。

最后一条原理面向未来：**解冻不是恢复原状，是冻结周期的间隙**。这次冻结的原因是源站侧的变更（封禁加数据停摆），没有任何证据表明下次不会再来一次——所以解冻日的全部动作都应该按「可重复操作」来写：探测有探测的脚本，schema 比对有比对的清单，结论复审有复审的模板。把解冻流程写成 SOP 的那一刻，下一次冻结就从一个事故降级为一个流程输入。**可持续更新架构的检验标准不是「解冻后跑得多顺」，是「再冻结时损失多小」**——本地快照是否完整、GitHub Actions 出口是否随时可用、个人线是否常转，这三样决定了你是在冻结里「停摆」还是只是「降级」。

## 二、数据支撑：冻结时间线、解冻判据与折旧清单

先把已经发生的事按时间线钉死，这是解冻日比对的基准。09-14：抓包确认全部端点可用，`data/meta/2026-09-14/` 有完整快照与抓取报告。09-15 至 09-16 上午：每日采集正常，updates.log 里 ok=true、时长几百毫秒、summary 有正常的升降变动（09-15 三次运行 heroesUp 5/heroesDown 5；09-16 04:26 出现过一次 `heroesLeft: 85`——全量下架的假信号，现在回看是源站异常的第一声咳嗽）。09-16 04:29 起：fetch 报 `code=42000 系统异常，请联系站长协助处理`，错误串里带本机出口 IP——封禁实锤，从此本机直连死亡，采集切换 GitHub Actions 出口。09-20 起：聚合、榜单、趋势、橱窗整体冻结，证据是 09-20 与 09-22 两份 summary 逐字一致、装备榜样本恒定在 1137509 场、连续多日 summary 全零变动；同窗口内 lineups 与 equipment-fit 两个接口仍有活动。这条时间线的用途：**解冻日的第一件事就是把当天的事件追加到这条线上**——哪个接口先动、样本量何时开始增长、schema 有没有变，都是要入档的事实。

解冻的判据要写得能防呆。冻结的判定用过三根指针：跨日快照哈希一致、样本量纹丝不动（1137509 恒定）、变动率全零。解冻的判定是同一组指针反向：**样本量相对冻结值发生增长**是最硬的一条（说明源站又在对局样本上做聚合运算了）；其次是跨日快照开始出现差异；再次是 summary 的 entered/left 恢复非零。注意一条防坑规则：**lineups 和 equipment-fit 在冻结期内就活着，它们的响应不代表解冻**——这两个接口的活跃是独立口径（第二百九十八章专门给它们标了「独立口径」），解冻判定必须看的是聚合与榜单那组指针。还有一条更细的：解冻初期可能出现「样本量增长但榜单不变」的中间态（源站分步恢复），中间态按冻结处理，别抢跑。

统计层结论的折旧清单要具体到每一条，解冻日按单逐项办手续。举三个真实样本说明折旧的三种形态：**翻转型**——痛苦面具在 fit-lift 口径里从 09-15 的 −8.3pp 翻到补丁后的 +9.6~11.5pp，方向都变了，这种结论解冻后不作任何沿用，直接重测；**衰减型**——炽热支配者从 +12.4pp 走到 +6.5pp，方向没变但幅度腰斩，沿用排序、作废数值；**稳定型**——魔律之刃四日稳定在 +27~28pp 且与联合查询互证，这类读数可以在新窗口的第一批数据里当「回归检验」用：新数据出来如果魔律还在头部且量级接近，说明新窗口的口径与旧窗口大体连续，其他结论的换血可以按常规节奏走；如果连它都面目全非，整包结论全部重测，一个不留。折旧清单的载体就是第二百九十九章的原子卡：每张带口径日期的卡，解冻日过一遍，标存活、降级或作废——**卡片系统在这里收回它的第二笔红利**：有出处的结论才办得动手续，没出处的结论连它自己什么时候过期都说不清。

窗口污染的账要算清楚，它决定解冻后多少天之内不许下结论。榜单接口的参数是 time=7——近七天的滚动窗口。设解冻日为 D，那么 D 日的榜单混着 6 天冻结期数据加 1 天新数据；D+1 日混 5 加 2……直到 D+7，窗口内最后一批冻结期数据才被挤出去。这意味着：**解冻后的头七天，榜单是新旧环境的加权混合物，且权重每天都在变**——混合物上算出的任何「趋势」都是数据构成的伪影，不是环境的变化。七天的依据是窗口长度本身，不是拍脑袋；如果源站解冻时连 time 参数口径一起改了（比如改成 time=1 或 time=30），翻新期就要按新口径重算——这正是 schema 检查要盯的参数之一。冻结期越长，这个等待越不可省：冻结四周后，混合窗口里的新旧比例是 7 比 0 起步，头三天的榜单几乎还是旧世界的遗照。

## 三、实操：解冻首周的 SOP

**Day 0（解冻确认日）：管道体检，不碰结论。**四件事。一，单点探测：从 GitHub Actions 出口对一个轻端点发一次请求，看 code 字段——42000 依旧说明封禁没解（接口活动与封禁解禁是两回事，都要查），正常响应才进下一步。二，schema 比对：把新响应与冻结前最后一份快照逐字段对比——字段增删、类型变化、id 口径变化、time 参数行为；任何漂移先改 `data/schema.md` 和前端 `ui/src/types.ts`，再谈采集。三，样本量核对：新快照的样本基数与冻结值 1137509 的关系——略增是正常恢复，重置或跳变要按新口径处理。四，管道演练：手动触发一轮 fetch-meta，核对 updates.log 落了 ok=true 且 summary 有真实变动（不是全零）；确认 08:53 的定时任务和 Actions 工作流都改回自动状态。**Day 0 的产出物是一份体检记录**，追加进冻结时间线：探测结果、schema diff 清单、样本量读数。四件事全部有脚本或清单，全程半小时——前提是解冻流程早就写好，这正是本章存在的意义。

**Day 1 至 Day 3：只采集，不下结论。**这三天唯一的任务是让快照序列重新长起来：每日快照照常入库，卡片系统照常运转（个人线不受影响），但**不更新任何环境类结论**——混合窗口里没有结论的容身之处。可以做的是准备工作：把折旧清单草拟出来（哪些卡预计要办什么手续，按第二部分的四种形态预分类）；把条件查询的脚本参数过一遍（comp-query、eq-combo-query 的候选阵容清单要不要按新环境换——换什么要等数据，但脚本本身可以先跑通空转测试）；准备好 09-14/09-15/09-20 三个对照快照的索引。另外确认卡牌库要不要重提取：**如果解冻伴随版本更新**（英雄面板、技能数值改动），跑 `node scripts/extract-database.mjs` 重新提取内嵌卡牌库，再 `node scripts/split-database.mjs` 拆分入库，机制层的 heroes/commanders/equipment/talents 四套 JSON 换血，并在数据里更新 version 标记；**如果只是数据源恢复而版本没动**，机制层一个字都不用动——这就是机制层和统计层分层的日常回报。

**Day 4 至 Day 7：逐步重建派生产物。**窗口过半（D+4 起），新数据在混合物中占比过四成，可以开始产出**标注了混合口径**的中间产物：条件查询（comp-stats）重跑一轮，产物标注「混合窗口，含冻结期样本」；meta-evolution 的跨日对比重启，但从 D 日重新起算序列号，不与冻结段拼接；仪表盘的灰色冻结徽章换黄色「窗口翻新中」。这四天产出的读数只做两个用途：给 Day 7+ 的正式结论提供方向预感，以及发现异常（如果 D+4 的混合读数与冻结前出现了巨大断裂，多半是版本更新落地了——这个信号决定折旧清单的规模要临时扩大）。**纪律红线只有一条：混合窗口的产物不进作战卡、不改判定线、不动 A/B 实验的先验**——所有会沉淀成决策依据的容器，等纯新数据。

**Day 7 及以后：正式换血。**纯新窗口的第一个完整读数日，按顺序办五件事。一，**先验换血**：个人模型的环境先验从冻结口径（混排池 40.2%/2.84 这类）换成新窗口读数，75 折的执行系数保留不动——环境变了，你的折扣没变。二，**条件查询全量重跑**：comp-stats、eq-combo-query 按新窗口重建，装备 fit 的完备排名重新排序，第二百九十一章的装备分配结论逐条对照。三，**结论折旧清单执行**：按折旧三形态（翻转/衰减/稳定）给每张统计层卡片办手续，作废卡归档不删除。四，**对抗性审查重跑**：第一百九十七章的对抗性验证方法与第二百九十七章的实验纪律整体过一遍新数据——偏差是数据源的属性，大概率原样健在（幸存者偏差不会因为解冻而消失），但样本结构变了，每条发现要重新确认「还成立」并注明重验日期。五，**A/B 与验证周期重启**：第二百九十七章的实验队列解冻，冻结前未跑完的实验一律作废重开（环境变了，旧实验的可比性前提没了）；验证周期的新先验按换血后的数字设。

最后一步是「恢复冻结就绪」。换血完成后，把本次解冻全程的经验回写进 SOP：探测脚本有没有漏判、schema diff 有没有意外项、折旧清单执行花了多久；然后确认三件常备物处于随时可用状态——本地快照的完整性（冻结期结束时最后一份有效快照完好归档）、GitHub Actions 工作流的可启动性（下次封禁时一键切换）、个人线的常转（matches 与验证周期不依赖任何外部数据）。**下一次冻结的损失 = 这三件的完好程度**——这是全章最值得记住的一行。

## 四、常见错误：五种解冻期事故

**错误一：解冻日等于结论日。**探测到接口恢复，当天就把榜单读数写进结论、更新作战卡、宣布环境变化——D 日的榜单里六天是冻结期样本，你读到的「环境」几乎还是旧世界的遗照，据此做的体系切换全是在给伪影打工。纠正：Day 0 只做体检，头三天只采集，结论等 Day 7 的纯新窗口；「解冻」和「可下结论」之间隔着一个窗口翻新期，这个间隔是窗口参数决定的物理量，不是耐心问题。补救：已经按 D 日读数做了决策的，把决策时间戳标注出来，Day 7 后用纯新读数重验一次——方向不变算运气好，方向翻转让损失可见，也比无感地错下去强。

**错误二：跨断点补数。**把冻结前的快照和解冻后的快照拼成一条连续序列画趋势、算斜率、做「解冻前后对比」——断点两侧是两个统计总体（样本结构、聚合口径、甚至游戏版本都可能不同），拼接序列的任何形态学读数都是伪影。纠正：断点纪律硬执行——序列在断点处分段，前段封存为「冻结期历史」，新序列从 D 日重新起算；一切「前后对比」只做定性级别的方向对照，且必须注明跨断点的口径风险。补救：已经拼了的图，在断点处切开重画；切开后如果新序列短得画不成曲线（头几天必然如此），就如实显示散点——**诚实显示两个点，好过漂亮显示一条假线**。

**错误三：旧结论自动复活。**解冻后新榜单的数字与冻结前「看起来差不多」，于是宣布所有冻结前结论自动续期——这个推理的漏洞在窗口污染：头几天的混合读数本来就会接近冻结前读数（旧样本占大头），「接近」恰恰是窗口还没翻新的证据，不是结论还成立的证据。假阳性复活的经典链条：D+1 读数像旧的 → 结论复活 → D+7 纯新数据翻转 → 决策已经按复活结论做了四天。纠正：续期不靠目测，靠折旧清单逐卡办手续；「稳定型」结论（魔律式）的续期确认必须等到 Day 7 后的纯新读数。补救：已按目测续期的，倒查每一条的确认日期——凡是在 Day 7 前确认的，一律降回「待重验」重走流程。

**错误四：只修管道不修地图。**解冻后采集一把跑通、快照照常落盘，皆大欢喜——但源站顺手改了字段名或加了字段，解析层静默丢数据，落盘的 JSON 是缺斤短两的空壳；典型信号是 updates.log 里 ok=true 但 summary 的变动计数连续多日全零。这就是「管道健康、地图过期」：schema.md 和 types.ts 是消费数据的地图，地图不改，管道越健康，产出的一致性错误越多。纠正：schema 比对是 Day 0 的硬步骤（本部分体检第二条），且后续一周每日快照做一次轻量字段校验（关键字段存在性 + 类型）；summary 全零连续三天即触发人工核查，哪怕管道报成功。补救：发现静默丢字段的，从最后一次字段校验通过的日期起，标注受影响快照为「口径存疑」，能重抓的重抓，不能重抓的在所有引用处注明缺陷。

**错误五：把解冻当永久。**解冻一周后，SOP 归档、告警下线、Actions 工作流闲置、本地快照的完整性检查也不再跑——系统回到「假设数据源永远健康」的松懈态，而下一次封禁或停摆到来时，一切从头排查。这次的冻结从 09-16 的第一声咳嗽到全面停摆只用了四天，解冻窗口如果同样短，松懈的代价就是下一轮 Day 0 从零开始写探测脚本。纠正：解冻流程的终点是「恢复冻结就绪」而不是「恢复正常」——三件常备物（快照完整性、备用出口、个人线常转）写进每周维护清单；仪表盘的四态徽章保留「灰色（源站冻结）」这个状态，让它永远一键可达。补救：已经松懈掉的，按本章第三部分的清单逐项恢复，一次性补齐——解冻期的从容是用冻结期的准备换的，这句话反过来说就是：今天的准备，是下下次解冻期的从容。

## 五、可迁移原则

1. **过期速度分三层：机制随版本、统计随窗口、方法不随任何东西。**解冻日的动作顺序由这条分层决定——先修机制层（若版本更新）、等统计层翻新、方法层全程在线；把资产按保鲜度分层存放，任何一次数据源震荡都知道什么该动什么不该动。
2. **先验管道，再碰结论。**解冻的第一反应是体检（探测、schema、样本量守恒），不是抓数后宣布胜利；混合窗口里的读数是新旧环境的加权混合物，权重未翻新之前，它不支撑任何结论。
3. **断点两侧是两个世界。**拼接序列画出的每一条趋势线都是伪影；断点前封存、断点后重起算，诚实地显示散点，好过漂亮地显示假线。
4. **结论续期要办手续，不靠目测。**折旧清单、三种形态（翻转、衰减、稳定）、逐卡办手续并记录日期——「数字看起来差不多」在窗口翻新期恰恰是旧样本占大头的症状，不是结论存活的证据。
5. **解冻不是恢复原状，是冻结周期的间隙。**可持续架构的检验标准是「再冻结时损失多小」：快照完整性、备用出口、个人线常转，三件常备物决定你下次是停摆还是降级——解冻流程写成 SOP 的那一刻，事故就降级成了流程输入，而下一个断点来临时，你只需要执行，不需要回忆。
